### Изменено 2026-09-04 — привязка userbot-аккаунта к каналу (ADR-0019)

- **У каждого канала — свой userbot-админ, постинг из его сессии.**
  Флаг `channels.userbot_admin` («какой-то userbot — админ») заменён
  ссылкой `tg_account_id` на конкретный аккаунт (миграция
  `e6b9d43a7f21`, только схема — привязка существующих каналов
  выполнена разово вручную, с бэкапом БД). Шлюз Telegram держит
  **пул клиентов MTProto** — по одному на вошедший аккаунт; публикация,
  чтение отложек и проверки прав адресуются аккаунту канала; лимит
  файла (2000/4000 МиБ) — по Premium именно этого аккаунта, статус
  Premium в списке аккаунтов честный у каждого подключённого.
- **Подключение канала через userbot — с явным выбором аккаунта**
  (авто-перебор привязал бы случайного из двух админов); на бот-пути
  и при перепроверке канала без привязки админ ищется опросом вошедших
  аккаунтов. Новые действия карточки канала: «Привязать userbot…»
  (с проверкой прав) и «Отвязать userbot». Перепроверка доступов
  меняет привязку только по подтверждённому ответу Telegram;
  подтверждённый отказ привязанного аккаунта снимает привязку.
- **Флуд-лимит стал пер-аккаунтным** (развитие ADR-0017): дозор слотов
  очереди отправки при флуде прекращает опрос только каналов
  провинившегося аккаунта — каналы других аккаунтов проверяются дальше.
- **Удаление аккаунта** гасит только его клиента (чужие подключения
  не рвутся); каналы отвязывает SET NULL, подтверждение удаления
  перечисляет каналы, которые останутся без userbot-админа.
- Документация: ADR-0019, data-model.md, channels.md,
  telegram-gateway.md, engine-api.md; тесты пула, привязок,
  перепроверки и миграции.

### Изменено 2026-09-04 — ключ API Telegram один на приложение (ADR-0018)

- **Пара api_id/api_hash больше не спрашивается у каждого аккаунта.**
  Это реквизиты приложения с my.telegram.org, а не аккаунта: с одной
  парой входят все userbot-аккаунты (как у обычных клиентов Telegram).
  Ключ выделен в таблицу `tg_api_credentials` (одна запись, `api_hash`
  шифруется — правило ADR-0009 сохранено) и правится в новом блоке
  «API Telegram» на «Настройки → Общие»; колонки `api_id`/`api_hash`
  удалены из `tg_accounts` (миграция `d8f2a61c4e93`, только схема —
  значения перенесены разово вручную, с бэкапом БД).
- **Диалог «Новый userbot-аккаунт» — два поля**: название и телефон;
  телефон обязателен (аккаунт без него — тупик: некуда слать код
  входа). Вход и активация userbot берут ключ из общей записи;
  без ключа — понятная ошибка с указанием, где его задать.
- Документация: ADR-0018, data-model.md, configuration.md, setup.md,
  engine-api.md, data-schemas.md; тесты ключа, обязательности телефона
  и миграции (аккаунты и сессии переживают удаление колонок).

### Добавлено 2026-08-27 — ADR-0017: бюджет запросов Telegram (sys-4)

- **ADR-0017** фиксирует предусловие этапа 2 (источники): все
  периодические чтения Telegram — через единый планировщик опроса
  с общим бюджетом частоты на аккаунт; публикация приоритетнее чтения;
  флуд-лимит останавливает весь опрос; планировщик — первая задача
  этапа 2, источники строятся только поверх него. Отдельный
  аккаунт-читатель — зафиксированный запасной ход, не оплачиваемый
  заранее.
- **Дозор слотов: флуд-лимит прерывает весь тик.** Раньше канал
  с флудом просто пропускался, и дозор продолжал стучаться в остальные
  каналы того же аккаунта — усугубляя лимит (Telegram растит сроки
  за настойчивость). Теперь `TelegramFloodError` завершает тик целиком,
  ждущие остаются ждать штатно, дозор возвращается по таймеру.

### Исправлено 2026-08-27 — щадящий догон и флуд-лимит (системный анализ, sys-1)

- **Флуд-лимит Telegram перестал быть ошибкой элемента.** Ответ сервера
  «подождите N секунд» (`FloodWaitError` у userbot, `TelegramRetryAfter`
  у бота) раньше сворачивался в общие классы и хоронил пост в ошибке —
  после простоя приложения хвост догоняющего залпа оседал в ERROR
  с ручным повтором каждого. Теперь оба транспорта переводят его
  в общий доменный класс `TelegramFloodError` (поле `retry_after_s`),
  а очередь отправки возвращает элемент в ожидание, ждёт ровно
  названный сервером срок и повторяет сама — по образцу обработки
  «слоты кончились». Карточка на время паузы получает пометку
  «Telegram просит подождать N с. Очередь ждёт и повторит сама»
  (поле `note` снимка, как у авто-битрейта в обработке видео).
  У userbot новый класс наследует и прежнюю «временную недоступность» —
  существующие обработчики работают без правок.
- **Догон после простоя — щадящий.** Между просроченными постами
  (правило «просрочка → сейчас», ADR-0016) очередь держит паузу
  `CATCHUP_INTERVAL_S` (30 с): накопившиеся за простой 40 постов
  выходят за ~20 минут, а не пулемётной лентой за минуту — подписчики
  видят «канал ожил», флуд-лимит не срабатывает. Постов «сейчас»,
  поставленных пользователем вручную, пауза не касается. ADR-0016
  и таксономия ошибок в `telegram-gateway.md` дополнены.

### Изменено 2026-08-26 — аудит: мёртвый код, наблюдаемость, имена (этап 4)

- **Удалён мёртвый и недостижимый код** (решение зафиксировано):
  режимы кадра `first`/`frame:N` (наследие порта makeVideo — из
  приложения недостижимы: `IntroSourceKind` их не содержит, интерфейс
  не предлагает); метод `has_unfinished` обеих очередей (два пути
  к одному ответу — истиной остался снимок `state()`, которым живёт
  панель); метод `clear_suggested_bitrate` формы видео (остался
  от модели «одна форма — один файл», вызовов не было).
- **Молчаливые исходы получили след в логе**: сбой ffprobe при сборке
  имени файла (`{quality}` пустой — причина теперь в логе); потоки-
  читатели ffmpeg при отмене больше не печатают трейсбек в stderr
  мимо `logging`.
- **Мелкие несостыковки ядра**: `EngineWorker.submit` отвечает понятным
  «Движок не запущен» и на закрытый цикл (раньше — «Event loop is
  closed» из глубин asyncio); убран переходный флаг `future=True`
  (SQLAlchemy 1.4); начальная миграция больше не зовёт приватный
  `Column._copy()`; комментарий о гонке создания ключа шифрования
  стал честным (окно сужается, а не закрывается).
- **Удаление неактивного userbot-аккаунта не рвёт живое подключение**:
  переподключение — только когда удалён именно активный (раньше любой
  аккаунт с сессией давал окно недоступности отправки).
- **Файловые операции — вне цикла событий движка** (`dirs_for`, сборка
  параметров обработки, проверки `bitrate_advice`): заснувший или
  сетевой диск больше не замораживает очередь отправки.
- **Единообразие интерфейса**: страница «Видео» перешла на общий
  `error_reporter`; выбор кадра чистит плитку общим `clear_layout`;
  границы партии кадров и цвета сводки — именованные константы;
  `_publish_channel` переименован в `_current_channel` (как
  на «Публикации»); подсказка имени в пакете не трогает уже убранную
  строку; докстринг `video_form` честно называет второй экспорт
  (`CollapsibleCard`); докстринг очереди видео объясняет
  потокобезопасность колбэка прогресса.

### Изменено 2026-08-26 — аудит: дубли сведены в единые точки истины (этап 3)

- **Перевод ошибок Bot API — одним маппером.** `check_token`
  и `get_bot_events` шли собственными except-лестницами с тремя
  дословными копиями перевода сетевой ошибки; теперь обе операции идут
  через `_bot_errors`. Отклонённый токен (Unauthorized) на всех путях —
  один класс `InvalidBotTokenError` (раньше путь отправки давал
  `ChannelCheckError`, и по классу нельзя было отличить битый токен
  от отсутствия прав).
- **Общие точки истины вместо копий**: разбор числового ID канала —
  одна функция `refs.numeric_chat_id` (класс ошибки — параметр
  транспорта); префикс «-100» — константа `CHANNEL_ID_PREFIX`;
  повторяющиеся тексты userbot («сессия недействительна»,
  «не администратор») — модульные константы (формулировки уже начинали
  расходиться); формат штампа конвейера — `PIPELINE_STAMP_FORMAT`
  со связкой к разбору имён, закреплённой тестом; фильтр видео
  в диалогах собирается из `VIDEO_SUFFIXES`
  (`video_dialog_filter`); перечень запрещённых символов имён —
  один на сервисы видео и подписей; дефолты формы параметров видео —
  из `PresetFields` движка; подсказки папок и диапазон периода опроса
  на «Настройках» — из констант движка; плейсхолдеры имени файла
  в подсказке — из экспорта `FILENAME_PLACEHOLDERS`; пара кнопок
  карточки файла («посмотреть»/«убрать») — общий помощник
  `file_action_buttons`; чтение «канал по id или понятная ошибка»
  в сервисе каналов — один помощник вместо пяти копий.
- **Фильтр каналов в «Вся очередь…» — по id, а не по названию**
  (названия каналов Telegram не уникальны): в `QueueItemDto` добавлен
  `channel_id`, фильтр и группировка «По каналам» различают тёзок;
  ручная арифметика индексов комбобокса заменена общим `DtoComboBox` —
  тем самым, что создан против этой арифметики.

### Исправлено 2026-08-26 — аудит: хвосты персистентной очереди (этап 2)

- **Удаление канала снимает его посты из живой очереди.** Раньше каскад
  БД удалял только строки: элементы в памяти оставались «зомби» — дозор
  вечно пропускал их с предупреждением «Канал не найден», а файлы
  ждущих оседали в папке очереди. Теперь удаление идёт через
  `Engine.delete_channel`: элементы снимаются как «Отмена» (файлы
  возвращаются в результаты), активная отправка обрывается (закрыто
  «известное упрощение» ADR-0016).
- **Диалог «Вся очередь…» больше не «съедает» итоговые плашки.** Две
  панели над одной очередью наперегонки снимали завершённые элементы;
  у панели появился режим зрителя (`dismiss_finished=False`) —
  завершёнными владеет только панель страницы «Публикация».
- **Дозор слотов останавливается, когда ждать некому** (как и обещал
  его докстринг): нет ждущих — нет фоновой задачи; следующая постановка
  поднимает дозор заново.
- **Карточка и плашка просроченного поста честны**: при публикации
  «сейчас» по правилу просрочки снимок для интерфейса обновляется —
  вместо «Отложенная запись создана» показывается «Опубликовано».
- **Папка очереди видна в настройках**: категория «Папки» получила
  строку «Очередь отправки» (ключ `video_queued_dir`), подписи
  описывают полный жизненный цикл processed → queued → published.
- Согласование с документацией: таксономия ошибок userbot
  в `telegram-gateway.md` дополнена `UserbotScheduleFullError`
  (и докстринг `gateway.publish`); ссылки свежего кода на замещённый
  ADR-0012 заменены на действующий ADR-0016; контракт `QueuePanel`
  описывает WAITING и необязательное поле `note`; из модели
  `publish_queue_items` убраны мёртвые умолчания, дублировавшие
  перечисления; тест полноты схемы знает про таблицу очереди.

### Исправлено 2026-08-26 — аудит: стыки персистентной очереди (этап 1)

- **Не-видео из папки результатов больше не застревает в папке
  очереди.** Постановка переносила в `queued/` любой файл из-под корня
  результатов, а после отправки в `published/` переезжали только видео —
  кадр-превью, отправленный как «Фото», или ролик, отправленный как
  «Документ», оставались в папке очереди навсегда. Решение: жизненный
  цикл processed → queued → published определён только для видео,
  не-видео из папки результатов отклоняется при постановке с понятной
  ошибкой (ADR-0016, уточнение).
- **«Повторить» работает для просроченного отложенного.** Повтор
  сначала перепроверял черновик, и валидация отклоняла прошедшее время —
  пост, упавший ночью, утром нельзя было повторить. Теперь просроченное
  время при повторе снимается, пост уходит «сейчас» — по общему правилу
  ADR-0016 «просрочка → сейчас».
- **Подтверждение выхода — только при активной загрузке.** Окно
  спрашивало «идёт отправка — загрузка оборвётся» при любых
  незавершённых элементах, включая ждущих слота, хотя персистентная
  очередь переживает выход (докстринг `closeEvent` это и обещал).
  У панели очереди появился признак «работа идёт прямо сейчас»
  (`active`), страница «Публикация» отвечает окну честным
  `upload_active` — ждущие выход не задерживают.
- **Гонка при быстрой смене канала на «Видео».** Поздний ответ движка
  мог подставить пресет прежнего канала в шаблон уже выбранного
  (и значения чужого пресета — в панель параметров). Обе цепочки
  «выбор → асинхронный ответ → применение» получили проверку
  актуальности выбора — по образцу `_is_stale` со страницы
  «Публикация».

### Добавлено 2026-08-26 — очередь сверх лимита отложек (ADR-0016)

- **Персистентная очередь отправки со слотами отложек.** Telegram
  ограничивает отложенные 100 на канал (Premium не увеличивает;
  горизонт — год; проверено по limits.tginfo.me и core.telegram.org) —
  теперь планировать можно больше: посты сверх лимита ждут в очереди
  со статусом «ждёт слота», свободные слоты перепроверяются раз
  в N минут (настройка «Очередь отправки» в «Настройках», по умолчанию
  5) и сразу после постановки; первым внутри канала уходит ближайший
  по дате. Просроченное время — публикация сразу обычным сообщением
  (это уже не отложка). Гонка с ручными отложками из клиента Telegram
  (`SCHEDULE_TOO_MUCH`) тихо возвращает элемент в ожидание. Очередь
  хранится в БД (`publish_queue_items`, миграция `b7f3d92c5a41`)
  и переживает перезапуск; ждущие публикуются только при запущенном
  приложении (первые ~100 выпускает сервер Telegram и без него).
  ADR-0012 замещён ADR-0016.
- **Папка очереди на диске** (`media/queued`, ключ `video_queued_dir`):
  жизненный цикл поста зеркалится папками processed → queued →
  published. Постановка переносит файл (с кадром-превью) из результатов
  в папку очереди — его нельзя случайно удалить со страницы «Готовых
  видео» или поставить повторно; отмена/снятие возвращает файл
  в результаты, отправка — в опубликованные. Файл-тёзка в папке
  очереди — понятная ошибка постановки; произвольные вложения с диска
  не трогаются.
- Интерфейс: сводка над панелью очереди («к отправке N, ждут слота M,
  ошибок K»), показываются ближайшие 20 карточек; подтверждение
  выхода спрашивает только про обрыв активной загрузки — ожидающие
  сохраняются и продолжаются при следующем запуске.
- **Полный просмотр очереди** — кнопка «Вся очередь…» на «Публикации»:
  живой диалог со всеми элементами (опрос тем же способом, что панель),
  сортировка («ближайшие сначала», «порядок постановки», «по каналам»)
  и фильтры (статус: к отправке / ждут слота / ошибки; канал — список
  каналов, живущих в очереди), итоговая строка «показано M из N»;
  действия у карточек те же («Отмена», «Повторить», «Убрать»).
  Правило показа — чистая функция `apply_view` (тестируется без Qt);
  у `QueuePanel` появился крючок `transform` — сортировка/фильтр
  без второй реализации панели.
- Надёжность: SQLite без пула соединений (`NullPool`) — отмена
  отправки посреди запроса к БД больше не оставляет заблокированное
  соединение («database is locked»); статусы пишутся в порядке
  «БД → память» — обрыв на полуслове при выходе не теряет исход.

### Аудит и рефакторинг 2026-08-25 (шесть направлений, полный проход)

Исправлено (корректность):

- **Старт с недоступным userbot больше не роняет приложение** (critical):
  `Engine.start()` после активации по сохранённой сессии повторно
  подключал userbot через шлюз без перехвата — запуск без сети падал,
  а при отозванной сессии приложение переставало открываться насовсем
  (войти заново было негде). Избыточный вызов убран, мёртвый
  `TelegramGateway.start()` удалён; регрессионный тест
  (`test_start_survives_unreachable_userbot`).
- Сбой конструктора движка (например, битый `DATABASE_URL`) молча
  подвешивал процесс: создание `Engine` перенесено под защиту потока
  (`worker.py`); незавершённые задачи при остановке цикла теперь
  отменяются штатно.

- **Пакетная отправка в Telegram** (ADR-0015): кнопка «Пакет из папки…»
  на странице «Публикация» — черновики постов из всех видео готовой

### Добавлено

- «Видео»: раздел «Готовые видео» показывает всю подпапку папки
  результатов, а не только последний результат — карточка на файл

  «Показать в папке», «Опубликовать…» и удалением. Список берётся
  по подпапке из панели параметров (той, куда уйдёт следующий
  результат) и перечитывается при её правке, загрузке пресета,
  открытии страницы и после обработки. Удаление спрашивает
  подтверждение и уносит вместе с видео его кадр-превью; путь вне
  папки результатов сервис отклоняет. В движке — `list_processed`
  и `delete_processed` (работа с диском — в отдельном потоке).
- Связанные словари подписей: поле может жить внутри другого поля
  канала («Character» внутри «Title», миграция `a8e4c73b9d52` —
  `caption_fields.parent_field_id` и `caption_values.parent_value_id`).
  При сборке поста список персонажей показывает только принадлежащих
  выбранному тайтлу и перестраивается сразу при его смене; значения без
  привязки видны всегда. Персонаж, введённый руками при выбранном
  тайтле, попадает в словарь уже внутри него, а тёзка из другого тайтла
  заводится отдельной записью. Удаление тайтла удаляет его персонажей
  (каскад в схеме) — редактор словаря предупреждает об этом. Связь
  задаётся выбором «внутри: …» у поля в диалоге «Поля подписи…»,
  правится вручную в редакторе «Словарь…» у каждого значения.
  Смена связи обнуляет привязки: они указывали в словарь прежнего
  родителя. Кольцо связей и родитель из другого канала отклоняются.
- Статус Telegram Premium у userbot: читается при каждом подключении
  (`get_me`) и определяет лимит на файл. Лимиты уточнены до настоящих
  значений Telegram (4000 частей по 512 КиБ = 2000 МиБ; с Premium —
  8000 частей = 4000 МиБ) — прежние «круглые» 2 ГиБ были чуть больше
  реального лимита. Статус виден на карточке аккаунта («Premium, файлы
  до 4 ГБ») и в подсказке возможностей на «Публикации»; проверка
  размера при публикации учитывает подписку.
- Рекомендуемый битрейт для крупного исходника: если выбранное на
  «Видео» видео больше лимита Telegram (2/4 ГБ по статусу аккаунта),
  движок считает битрейт под итоговый размер «лимит минус 1 %»
  (бюджет × 0,99 × 8 / длительность после обрезки − 192 кбит/с аудио)
  и подставляет его в «Качество, Мбит/с» — только поверх
  «0 — как в оригинале», заполненное поле не трогается.

- Имя файла по шаблону вписывается в лимит Telegram
  (`TELEGRAM_MAX_STEM_CHARS` = 78 символов стема — длиннее сервер молча
  режет и чистит): стем обрезается до конца последнего законченного
  слова, висячие знаки препинания убираются — без обрубков слов
  на конце; сплошное слово без разделителей режется как есть.
  Байтовый предел файловой системы (240) действует поверх (актуален
  для эмодзи — 4 байта на символ).
- Опытным путём вычислены правила Telegram для имён файлов при загрузке
  (57 проб userbot): стем ≤ 78 символов Юникода хранится как есть,
  длиннее — обрезка до 63–64 символов с чисткой (скобки, `?`, `~`
  удаляются; пробел, дефис, внутренние точки → `_`); управляющие
  символы заменяются всегда. Документ —
  [docs/03-modules/telegram-filenames.md](docs/03-modules/telegram-filenames.md);
  текущий предел рендера имени (240 байт) для Telegram слишком щедрый.
- Очередь отправки: кнопка «Повторить» у элемента с ошибкой (рядом
  с «Убрать») — возвращает пост в очередь на новую попытку без
  повторного заполнения формы. Черновик перепроверяется, как при
  постановке (файл мог исчезнуть, отложенное время — пройти);
  если неудачная попытка успела переименовать файл, повтор уходит
  уже под новым именем.
- Правка существующего шаблона подписи: кнопка «Изменить…» у шаблона
  в диалоге «Поля подписи…» загружает его в форму (имя, состав полей
  с порядком, шаблон имени файла); «Сохранить изменения» перезаписывает
  шаблон (смена имени — переименовывает), «Отменить правку» возвращает
  форму к сборке нового. Раньше шаблон приходилось составлять заново.
- «Расписание»: фильтр по каналам — чекбоксы над списком (по одному
  на канал с отложенными записями), выбор переживает «Обновить»;
  карточка записи перестроена: дата и время публикации — первой
  строкой, жирным и акцентным цветом темы, ниже текст и канал.
  В `ScheduledPostDto` добавлен `channel_id` (фильтр по id, названия
  не уникальны).
- Очередь отправки: в карточке элемента виден момент публикации —
  «публикация: 18.07.2026 20:30» (местное время) для отложенного поста,
  «публикация: сейчас» для немедленного. Момент передаётся в элементе
  очереди полем `when` (признак «отложенный» из него выводится).

### Исправлено

- **Обрыв сети больше не убивает userbot до перезапуска приложения.**
  Telethon, исчерпав свои попытки переподключения (минуты без сети),
  остаётся отключённым насовсем — из-за этого публикация и проверка
  доступов отвечали «нет связи или userbot отключён» даже после
  восстановления сети. Теперь транспорт MTProto перед каждой операцией
  проверяет соединение и при обрыве переподключается сам (одно
  переподключение на все ждущие операции); сессия при этом
  перепроверяется — если её отозвали за время простоя, ошибка сразу
  ведёт на повторный вход.

### Исправлено (читаемые ошибки, 17.07.2026)

- **В интерфейс больше не попадают дампы ошибок.** Три уровня защиты:
  пути из параметров обработки (вотермарк, картинка заставки)
  проверяются до запуска ffmpeg — несуществующий файл даёт точную
  причину с подсказкой; при падении ffmpeg в текст ошибки попадает
  только суть (строка с причиной + итог, полный журнал — в лог);
  общий заслон в мосте интерфейса — доменные ошибки движка
  (наследники нового `EngineError`) показываются как есть, а любое
  неожиданное исключение (например, многострочные ошибки СУБД)
  сворачивается в короткую «внутреннюю ошибку» с деталями в логе.
  Ошибка хранилища ключей (keyring) и сбой переименования файла
  переведены в доменные. Контракт «все доменные ошибки — EngineError»
  закреплён тестом.

### Исправлено (аудит и рефакторинг 17.07.2026)

- **Повторный вход userbot действует сразу**: активация закрывает
  прежнего клиента MTProto и применяет новые реквизиты (раньше после
  отзыва сессии или входа во второй аккаунт движок молча продолжал
  работать на старом клиенте до перезапуска приложения).
- **Запуск без сети больше не роняет приложение** при сохранённой сессии
  userbot: ошибка подключения при старте логируется, окно открывается;
  то же — при сбое чтения темы/геометрии окна (откат к умолчаниям)
  и при несовпадении ключа шифрования секретов (понятная ошибка
  `SecretDecryptionError` вместо пустого текста).
- **Целостность БД**: включена проверка внешних ключей SQLite
  (`PRAGMA foreign_keys=ON` на каждом соединении) и объявлены политики
  удаления (миграция `c1a4b83f7e29`): удаление канала каскадом уносит
  настройки и подписи (раньше таблицы подписей оставались сиротами),
  удаление бота отвязывает каналы (раньше висячая ссылка могла
  «прилипнуть» к чужому боту при переиспользовании id). Удаление
  активного userbot-аккаунта отключает клиента и переподключает userbot
  по оставшимся сессиям. Заодно закрыто расхождение схемы с моделями
  (nullable-таймстемпы таблиц подписей) — теперь его ловит постоянный
  тест «схема == модели».
- **Ошибки userbot разведены по классам** (не подключён / нет связи /
  сессия отозвана / подтверждённый отказ): перепроверка доступов канала
  больше не сбрасывает флаг userbot-админа при мигнувшей сети (раньше
  канал молча терял отложенные посты и большие файлы); сессия проверяется
  при подключении — «сессия отозвана» видна сразу, с инструкцией.
- **«Расписание» устойчиво**: опрашиваются только userbot-каналы
  (у бот-канала отложенных не бывает), ошибка одного канала не роняет
  весь список (раньше один бот-канал ломал страницу целиком).
- **«Публикация»: выбор канала восстанавливается по id, не по позиции
  в списке** — при изменении состава каналов между показами страницы
  пост не может молча уйти в другой канал.
- **Цикл событий движка не блокируется**: перенос опубликованного видео
  (гигабайты между дисками) и ffprobe имени файла ушли в отдельные
  потоки; чтение stderr ffmpeg — параллельным потоком (болтливый ffmpeg
  мог навсегда заблокировать кодирование на переполненном буфере канала).
- Публикация: движок проверяет лимит userbot (2 ГБ) до загрузки
  и отказывает выключенному каналу (правило системы, а не фильтр
  интерфейса); `get_bot_events` переводит конфликт вебхука в понятный
  текст.

  в 320×320 с сохранением пропорций; для видео без превью-соседа —
  случайный кадр из середины. Метаданные видео (длительность, размеры)
  Telethon извлекает через новую зависимость `hachoir` — без них
  Telegram игнорирует миниатюру и рисует плитку с неверными пропорциями.
- Страница «Публикация» — единая точка создания постов (ADR-0011):
  тип контента сегментами (текст, фото, видео, аудио, файл), канал,
  текст/подпись, «сейчас» или дата+время, прогресс загрузки файла.
  Весь контент публикует userbot (лимит Bot API — 50 МБ на файл,
  у MTProto — 2 ГБ); в движке — единая сущность `PostDraft`
  и `PostsService.publish()`; путь через бота законсервирован для ИИ.
  Кнопка «Опубликовать…» на карточке результата «Видео» открывает
  «Публикацию» с предзаполненным файлом; «Расписание» — только список
  отложенных.
- Выбор качества видео в пресете: целевой битрейт в Мбит/с или
  «как в оригинале» (по умолчанию — битрейт исходника; если ffprobe
  его не сообщил — постоянное качество CRF 20).
- Прогресс обработки видео с процентами: ffmpeg отчитывается через
  `-progress pipe:1`, полоса и подпись «Кодирование: NN%» на странице
  «Видео».
- Подготовка видео (порт из `makeVideo`, слайс A): чистый модуль
  `engine/video/` (FullHD, вотермарк с окном показа, заставка для превью,
  обложка), пресеты обработки (CRUD), страница «Видео» с запуском
  обработки и результатами в `media/processed/`. Публикация видео —
  следующий слайс.
- Первый пост: публикация «сейчас» через бота; отложенные посты
  создаются прямо в канале (серверное планирование Telegram через
  userbot, ADR-0010); страница «Расписание» читает отложенные из
  Telegram. Userbot подключается при старте и сразу после входа.
- Логирование в файл с ротацией: `logs/pxcontrol.log` (~2 МБ × 5),
  уровень через `LOG_LEVEL`; ошибки операций движка пишутся с полным
  трейсбеком; в лог попадает контекст подключения канала (бот, ввод,
  нормализация).
- Диагностика «Где состоит бот?» на карточке бота: события Telegram
  за 24 часа (добавления в каналы/группы и права) — в диалоге и в логе.

### Исправлено

- Имя файла по шаблону обрезалось на произвольных 150 символах —
  длинные названия теряли хвост ещё при формировании. Теперь предел —
  в байтах UTF-8 (240, с учётом расширения), как того требуют файловые
  системы (ext4 — 255 байт на имя): латиница получила ~236 символов,
  кириллица режется по честному байтовому пределу без битых символов
  (раньше 150 кириллических букв = 300 байт — файл не переименовался бы
  вовсе).
- Обложка уводила индекс `moov` в конец файла: главный проход ставил
  `-movflags +faststart` (moov в начало — для перезалива и проигрывания
  «на лету»), но шаг вшивания обложки ремуксил без флага и возвращал
  moov в хвост. Теперь `+faststart` есть и на вшивании обложки.
- Цвета вотермарка искажались (красный зеленел): overlay по умолчанию
  смешивает с цветностью в четверть разрешения (yuv420), и тонкие
  штрихи перенимали цвет соседей, а RGB→YUV шёл матрицей bt601 вместо
  bt709. Теперь конверсия — явно bt709, смешивание — в yuv444.
- Заставка из своей картинки валила обработку, если пропорции картинки
  отличались от видео: `xfade` требует одинаковых размеров входов.
  Теперь размер кадра считается в Python (`fitted_size`) и задаётся
  явно и видео, и заставке; чужая картинка вписывается с чёрными
  полями по центру. В диалоге пресета поля заставки активны только
  при включённом переключателе — раньше выключенная заставка выглядела
  настроенной.
- Вотермарк накладывался с искажением пропорций и размера: устаревший
  фильтр `scale2ref` в ffmpeg 8 считает размеры неверно — заменён
  на `scale` со вторым входом-эталоном (`rw`, высота `-2` сохраняет
  пропорции). Заодно стала наглядно работать прозрачность вотермарка.
- Подключение канала: ID с пробелами внутри и ссылки `t.me/c/…`
  распознаются; инвайт-ссылки (`t.me/+…`) отклоняются с пояснением;
  в ошибках теперь виден оригинальный ответ Telegram; подсказка
  в диалоге — как узнать ID приватного канала.
