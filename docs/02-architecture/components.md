# Компоненты системы

> Статус: 🟢 актуально · Обновлено: 2026-09-12 · Владелец: olegosx

## Назначение документа

Перечислить компоненты приложения, их зону ответственности и связи между
ними. Уровень детализации — крупнее, чем модули, но конкретнее, чем общий
обзор.

## Состав

### Интерфейс (PySide6 + QFluentWidgets)
- Страницы: «Каналы», «Видео» (пресеты и подготовка), «Публикация»
  (все типы контента + шаблоны подписей), «Расписание» (отложенные
  из Telegram), «Настройки» (категории слева: «Общие», «Аккаунты»).
- К движку обращается только через `EngineWorker.submit()` +
  мост `run_in_engine` (результаты возвращаются сигналами Qt; тип
  результата сквозной — mypy сверяет корутину с колбэком). Поток
  движка излучает сигналы только на бессмертном маршрутизаторе моста
  (`_Dispatcher`): излучение на одноразовых объектах гонялось с их
  `deleteLater` и падало сегфолтом в Qt (ловилось дампами ядра);
  повторяющиеся события (прогресс) идут тем же путём — `ui_callback`.
- Ошибки: пользователю показываются только читаемые тексты. Доменные
  ошибки движка (наследники `EngineError`, `engine/errors.py`) мост
  показывает как есть; любое неожиданное исключение (ошибки СУБД,
  библиотек) сворачивается в короткую «внутреннюю ошибку», полные
  детали — в лог (`user_message`). Новая доменная ошибка обязана
  наследовать `EngineError` — контракт закреплён тестом
  `test_errors.py`.
- Два вида окон ([ADR-0023](decisions/0023-work-windows-and-question-dialogs.md)):
  **короткий вопрос** — диалог-маска библиотеки (`MessageBoxBase`:
  подтверждение, ввод кода, небольшая форма) и **рабочее окно** —
  `WorkDialog` с рамками от системы (словарь, подписи, участники,
  пакеты, очередь и правка её элемента, выбор кадра): двигается,
  меняет размер, содержимое прокручивается само. Оба показываются через `exec_dialog`.
  Стили библиотечных виджетов не переопределяются — их лист
  принадлежит библиотеке (там же, п. 5).
- Общие элементы страниц — `pages/common.py`: карточки-строки, диалоги
  (показ — через `exec_dialog`, он же убирает диалог после закрытия),
  комбобокс списка DTO (`DtoComboBox` — выбор сохраняется по id,
  не по позиции), панель очереди движка (`QueuePanel` — общий каркас
  панелей «Публикации» и «Видео»: опрос состояния, карточки
  с прогрессом и действиями «Отмена/Повторить/Убрать», точечное
  обновление — меняется только изменившаяся карточка (`plan_cards`),
  а не весь список; крючки `editable`/`fill_body` раскрывают карточку
  формой правки, `leading` рисует начало шапки — логотип сообщества
  и цветную метку слота времени; все три передаёт только очередь
  отправки, ADR-0016), логотип сообщества (`community_logo` — аватар
  из кэша статистики, без него буква названия на подложке; общий
  для плиток дашборда и карточек очереди), метка слота
  (`slot_label`/`slot_color` — цвет выводится из времени публикации,
  один слот всегда одного цвета), строка
  «сейчас/дата+время» (`WhenRow`), красная подпись ошибки валидации
  (`ErrorLabel`), строка выбора и прокручиваемый список пакетных
  окон (`SelectionRow`, `list_area` — область без заданной
  высоты: полосу прокрутки она показывает сама).

### Движок (engine)
- UI-независимый пакет: сервисы (`accounts`, `communities`, `posts`,
  `video`, `captions`, `settings` — реестр ключей и хранение настроек
  ([ADR-0013](decisions/0013-settings-storage.md)), `publish_queue` —
  персистентная очередь отправки со слотами отложек
  ([ADR-0016](decisions/0016-persistent-publish-queue.md)),
  `video_queue` — очередь обработки видео, одиночной и пакетной
  ([ADR-0014](decisions/0014-video-processing-queue.md)),
  `maintenance` — обслуживание сообществ: чистка служебных записей
  и удалённых аккаунтов ([ADR-0026](decisions/0026-community-maintenance.md))),
  модель данных, шлюз Telegram.
- **Каркас заданий** (`engine/jobs.py`,
  [ADR-0025](decisions/0025-job-queue-framework.md)) — общий жизненный
  цикл всех трёх очередей: статусы (`JobStatus`), последовательный
  воркер, доля выполнения, отмена, повтор, отсрочка, кооперативная
  остановка. Предметные исходы («кончились слоты отложек», «файл
  исчез») переводит сам исполнитель задания; персистентность — дело
  конкретной очереди.
- Работает в фоновом потоке со своим циклом событий asyncio
  ([ADR-0006](decisions/0006-desktop-pyside6.md)) — сетевые операции
  и кодирование видео не блокируют интерфейс.
- Отложенные посты публикует сервер Telegram
  ([ADR-0010](decisions/0010-posts-fire-and-forget.md)) — своего
  планировщика в приложении нет.

### Модуль обработки видео (`engine/video/`)
- Чистый модуль поверх `ffmpeg`: файл + параметры → обработанный файл
  и кадр-превью. Не знает про Telegram, каналы и БД.
  Подробно — [video-processing.md](../03-modules/video-processing.md).

### Шлюз Telegram (`engine/telegram/`)
- Два транспорта за одним фасадом: MTProto — публикация и чтение,
  Bot API — проверки и диагностика ([ADR-0011](decisions/0011-publish-via-userbot.md)).
- Рядом с пулом транспортов — пул **дорожек аккаунтов**
  ([ADR-0024](decisions/0024-telegram-account-lane.md)): очередь
  обращений, зазор между запросами, приоритет операции и общая
  заморозка после флуд-лимита. Правило «лимит действует на аккаунт»
  живёт здесь одно на всё приложение.
  Подробно — [telegram-gateway.md](../03-modules/telegram-gateway.md).

### Хранилище данных
- SQLite в папке приложения, миграции Alembic при старте; секреты
  шифруются, ключ — в системном хранилище ОС
  ([ADR-0009](decisions/0009-config-secrets-in-db.md)).
  Модель — [data-model.md](../05-data/data-model.md).

## Таблица ответственности

| Компонент | Отвечает за | Не отвечает за | Зависит от |
|---|---|---|---|
| Интерфейс | формы, навигация, показ прогресса/ошибок | бизнес-логику, сеть | Движок (через EngineWorker) |
| Движок (сервисы) | бизнес-логика, валидации, оркестровка | отрисовку | БД, шлюз Telegram, модуль видео |
| Модуль видео | ffmpeg-конвейер, превью | Telegram, БД | ffmpeg/ffprobe |
| Шлюз Telegram | транспорты, перевод ошибок | бизнес-правила | aiogram, Telethon |
| Хранилище | схема, миграции, шифрование секретов | файлы медиа (только пути) | SQLite, keyring |
