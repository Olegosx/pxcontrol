# Порядок запуска и остановки

> Статус: 🟢 реализовано в каркасе · Обновлено: 2026-09-05 · Владелец: olegosx

## Назначение документа

Описать, как приложение запускается и останавливается, и как связаны
интерфейс и движок во время работы. Соответствует коду в `src/pxcontrol/`.

## Модель потоков

- **Главный поток** — интерфейс на PySide6 и цикл событий Qt.
- **Фоновый поток `engine`** — движок со своим циклом событий asyncio:
  база данных, шлюз Telegram, обработка видео. Планировщика нет —
  отложенные посты хранит и публикует сервер Telegram (ADR-0010).

Так тяжёлая и асинхронная работа не блокирует окно (см.
[ADR-0006](decisions/0006-desktop-pyside6.md)). Интерфейс вызывает корутины
движка через `EngineWorker.submit(coro)` — она безопасно планирует корутину
в цикле движка из потока интерфейса и возвращает `Future`.

## Порядок запуска

Реализован в `app.run()` и `EngineWorker`:

1. **Настройки** — `get_settings()` читает переменные окружения и `.env`.
2. **Логирование** — `setup_logging(level)`.
3. **Движок в фоновом потоке** — `EngineWorker.start()` поднимает поток
   `engine`, создаёт цикл asyncio и выполняет `Engine.start()`:
   1. инициализация базы данных — миграции Alembic (`Database.init()`);
   2. прогрев кэша настроек — `SettingsService.prime()` (ADR-0013):
      дальше синхронные читатели (путь ffmpeg и т.п.) берут значения
      из памяти;
   3. активация userbot по сохранённой сессии, если в БД есть аккаунт.
      Неудача подключения (нет сети, сессия отозвана) не мешает
      запуску: активация ловит её сама, приложение работает дальше,
      а транспорт чинится первой же операцией при появлении сети.
      Bot API соединений не держит — боты работают по токену
      на операцию, отдельного шага подключения у них нет;
   4. восстановление очереди отправки из БД (ADR-0016): неотправленные
      элементы возвращаются в работу, ждущим слота отложек сразу
      выполняется проверка слотов (поэтому шаг — после userbot);
   5. разовая уборка папок (ADR-0016, «Уборка опустевших папок»):
      пустые папки дерева очереди — остатки отработанных пакетов
      (файлы живых элементов уже на местах после шага 4) — удаляются
      вместе с их опустевшими зеркалами в результатах; сбой уборки
      запуску не мешает.
   Создание движка и `Engine.start()` выполняются под общей защитой:
   любая ошибка (включая сбой конструктора) пробрасывается
   в `EngineWorker.start()`, который ждёт готовности движка.

   Отдельного планировщика нет: отложенные посты хранит и публикует
   сервер Telegram (ADR-0010), «догон» не требуется.
4. **Интерфейс** — создаётся `QApplication`, показывается `MainWindow`.
5. **Цикл событий Qt** — `app.exec()` (блокирует главный поток до закрытия окна).

## Порядок остановки (обратный)

При выходе из `app.run()` вызывается `EngineWorker.stop()`:

1. цикл движка останавливается (`loop.stop()` из главного потока);
2. выполняется `Engine.stop()` — в обратном порядке:
   очередь отправки (`publish_queue.shutdown`, ADR-0016) →
   очередь обработки видео (`video_queue.shutdown`, ADR-0014) →
   сервис видео (`video.shutdown` — временные кадры) →
   шлюз Telegram (`stop`) → база данных (`close`).
   Очереди гасят свои фоновые задачи **кооперативно** (ADR-0020):
   событие остановки, задачи выходят в безопасных точках, запросы
   к БД не обрываются; жёстко отменяется только активная отправка
   в Telegram (недосланное сервер не публикует);
3. задачи, поставленные из интерфейса и не успевшие завершиться,
   отменяются (их блоки `finally` выполняются, asyncio не ругается
   на «destroyed but pending»); порядок именно такой — отмена всех
   задач до `Engine.stop()` убивала бы воркеров очередей жёстко,
   посреди запроса к БД (ADR-0020);
4. фоновый поток завершается (`join`).

## Headless-режим (без интерфейса)

`app.run_headless(seconds)` запускает только движок — для проверки и тестов
без графики. На нём держится дымовой тест `tests/test_smoke.py`.
