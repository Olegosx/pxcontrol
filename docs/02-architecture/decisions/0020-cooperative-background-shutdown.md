# ADR-0020. Кооперативная остановка фоновых задач движка

> Статус: accepted
> Дата: 2026-09-05 · Автор: olegosx
>
> Уточняет [ADR-0016](0016-persistent-publish-queue.md) (очередь
> отправки) и порядок остановки из [ADR-0006](0006-desktop-pyside6.md);
> закрепляет паттерн остановки, введённый в [ADR-0014](0014-video-processing-queue.md).

## Контекст

Фоновые задачи движка (воркер отправки, дозор слотов и внеплановые
проверки в `PublishQueue`) останавливались жёсткой отменой
(`task.cancel()`). Отмена может застать задачу посреди запроса к БД —
тогда соединение aiosqlite бросается с запросом «в полёте»: рабочий
поток соединения доделывает запрос уже после закрытия цикла событий
и падает в `call_soon_threadsafe` с «Event loop is closed». Симптомы,
подтверждённые диагностикой 2026-09-05 (серии прогонов с прижатием
к одному ядру CPU):

- `PytestUnhandledThreadExceptionWarning` из aiosqlite в тестах
  (5 из 10 прогонов под нагрузкой); предупреждение приписывается
  следующему по порядку тесту, поэтому «виновник» плавает;
- плавающие `ResourceWarning` о незакрытых соединениях (3–9 на прогон);
- плавающее падение `test_flood_on_slot_check_skips_rest_of_account`
  (1 из 60 под нагрузкой): тест синхронизировался с фоновой проверкой
  слотов через `sleep(0.05)` настенного времени, а длительность самой
  проверки растёт под нагрузкой — тик «догонял» тест после обнуления
  счётчика;
- в продакшене тот же дефект скрыт двумя слоями: `EngineWorker._run`
  перед `Engine.stop()` жёстко отменяет **все** задачи цикла — воркеры
  очередей гибнут до того, как их успеет погасить собственный
  `shutdown()` (вопреки комментарию в `_cancel_pending`); плюс ветка
  успеха `_send` выставляла DONE в память **до** удаления строки из БД —
  падение приложения в этом окне оставляло строку pending и вело
  к повторной отправке поста после рестарта.

Действующие силы: `Database` работает без пула соединений (`NullPool`,
осознанный выбор — см. комментарий в `database.py`), поэтому каждая
сессия — отдельное соединение aiosqlite со своим потоком; обрыв
недосланной загрузки в Telegram при остановке — желаемое поведение
(ADR-0016: SENDING не персистится, элемент уйдёт повторно);
`ProcessingQueue` (ADR-0014) уже останавливается кооперативно — флаг
`_closing` плюс ожидание воркера с таймаутом, без отмены.

## Решение

Закрепляются три инварианта; паттерн `ProcessingQueue` становится
нормой для всех фоновых задач движка.

1. **Жизненный цикл: владелец фоновой работы обязан уметь её
   дождаться.** `PublishQueue.shutdown()` останавливает задачи
   кооперативно: событие остановки (`asyncio.Event`), которое задачи
   проверяют в безопасных точках; паузы воркера (флуд-пауза до минут,
   пауза догона 30 с) и сон дозора ждут это событие с таймаутом-сроком
   (`wait_for(stop.wait(), timeout)`) — остановка прерывает их сразу,
   не обрывая запросов к БД. Жёсткая отмена остаётся ровно в одном
   месте — активная задача отправки в Telegram (обрыв недосланной
   загрузки — доменное поведение). Чтобы отменяемая задача
   действительно не содержала запросов к БД, публикация разделена
   на две фазы: `PostsService.prepare_publish` (проверки, чтения БД,
   переименование — выполняется в воркере, которого не отменяют)
   и `PostsService.transmit` (сеть и перенос файла — отменяемая
   задача); `publish` остаётся композицией фаз для прямых вызовов.
   Отмена или остановка, пришедшая во время подготовки,
   обрабатывается флагом после её завершения — сеть не начинается.
   Каждая задача дожидается с таймаутом-страховкой; по его
   истечении — жёсткая отмена как последнее средство. После возврата из
   `shutdown()` гарантия: ни одной живой задачи, ни одного запроса
   к БД в полёте — ровно то, что `Database.close()` молча предполагает.

2. **Согласованность состояния: «сначала БД, потом память» — без
   исключений.** Правило, уже действующее в ветках WAITING/PENDING/
   ERROR метода `_send`, распространяется на ветку успеха: строка
   удаляется из таблицы **до** выставления DONE в память. Наблюдатель
   (интерфейс, тест), увидевший статус в памяти, знает: работа с БД
   по нему завершена. Побочный выигрыш — исчезает окно повторной
   отправки поста при падении между «DONE в памяти» и удалением строки.

3. **Наблюдаемость фона: детерминированная точка присоединения вместо
   сна.** У очереди появляется публичный метод `settle()` — дождаться
   завершения внеплановой проверки слотов. Тесты синхронизируются
   с фоном через него; синхронизация через `sleep(N)` настенного
   времени запрещается как гонка по построению.

Порядок остановки приложения приводится в соответствие с этими
инвариантами: `EngineWorker._run` сначала выполняет `Engine.stop()`
(компоненты гасят свои задачи сами, кооперативно), и только затем
отменяет уцелевшие задачи цикла — к этому моменту там остаются лишь
вызовы, поставленные из интерфейса в момент закрытия.

## Альтернативы

- **Оставить жёсткую отмену, «дочищать» соединения.** SQLAlchemy
  не отдаёт наружу соединение, брошенное отменённой задачей, —
  закрыть его некому; `engine.dispose()` закрывает только вернувшиеся
  в пул. Отклонено: механизма нет.
- **Структурная конкуренция (`asyncio.TaskGroup`).** Требует объемлющей
  области видимости на всё время жизни очереди — перестройка движка
  ради того же результата. Отклонено: кооперативный флаг уже принят
  в проекте (`ProcessingQueue`) и достаточен.
- **Точечные правки тестов** (увеличить `sleep`, фильтр предупреждений,
  перезапуск упавших, ожидание приватных задач из тестов). Отклонено:
  лечат симптом — окно гонки сдвигается, утечка соединений остаётся,
  тесты связываются с внутренностями класса.

## Последствия

- **Плюсы:** остановка не рвёт запросы к БД ни в тестах, ни
  в приложении; уходит класс предупреждений aiosqlite/ResourceWarning;
  флейк-тест чинится детерминированной синхронизацией; закрывается
  окно дубля поста при падении; обе очереди движка следуют одному
  паттерну остановки.
- **Минусы / риски:** остановка ждёт завершения текущих коротких
  операций (страховочный таймаут ограничивает ожидание; худший
  случай — сетевое чтение слотов, оно ограничено таймаутами MTProto);
  `settle()` расширяет публичную поверхность очереди на один метод.
- **Ограничение (фиксируется осознанно):** обрыв запроса к БД задачей,
  отменённой **извне** движка (вызов из интерфейса, отменённый
  в момент закрытия), остаётся возможным — это общее свойство связки
  SQLAlchemy+aiosqlite. После смены порядка в `EngineWorker._run` такие
  задачи отменяются уже после `Database.close()`, когда запросов
  в полёте у них нет; отдельного механизма не строим, пока нет
  наблюдаемого симптома.
- **Что нужно сделать дальше:** реализовано вместе с решением —
  `publish_queue.py` (событие остановки, `settle()`, порядок в ветке
  DONE, отменяемая задача только вокруг передачи), `posts.py`
  (разделение `prepare_publish`/`transmit`), `worker.py` (порядок
  остановки), тесты очереди (фикстура с гарантированной остановкой,
  синхронизация через `settle()`, тесты отмены и остановки во время
  подготовки), `runtime.md` (описание порядка остановки). Приёмка
  2026-09-05: 30 прогонов файла тестов в покое и 15 под голоданием
  CPU — ноль падений, ноль предупреждений aiosqlite/ResourceWarning
  (до решения: падение 1 из 60, предупреждения в каждом прогоне).
