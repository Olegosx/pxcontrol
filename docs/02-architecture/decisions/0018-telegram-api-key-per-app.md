# ADR-0018. Ключ API Telegram — один на приложение

> Статус: accepted
> Дата: 2026-09-04 · Автор: olegosx
>
> Уточняет [ADR-0007](0007-hybrid-botapi-mtproto.md) (userbot)
> и [ADR-0009](0009-config-secrets-in-db.md) (секреты в БД).

## Контекст

Пара `api_id`/`api_hash` с my.telegram.org — реквизиты **приложения**,
а не аккаунта: с одной парой входят сколько угодно телефонов (так
устроены и обычные клиенты Telegram — у них пара вшита прямо в код,
скрыть её в распространяемом клиенте невозможно в принципе;
безопасность аккаунта держится на коде входа, 2FA и сессии).

В прежней модели пара хранилась в каждой строке `tg_accounts`
и запрашивалась при добавлении каждого аккаунта — реквизиты приложения
были смешаны с реквизитами пользователя. Это дефект модели данных:
повторный ввод одного и того же и ложное впечатление, что ключ
принадлежит аккаунту.

## Решение

1. **Ключ приложения — одна запись** в таблице `tg_api_credentials`
   (`api_id`, `api_hash` 🔐). `api_hash` — секрет средней ценности
   (утечка грозит баном api_id, не аккаунтов), но шифрование здесь
   бесплатно (`EncryptedStr` — одна аннотация) и сохраняет единое
   правило ADR-0009: всё секретное — шифрованными колонками, без
   категории «полусекрет открытым текстом». В `app_settings` ключу
   не место по тому же правилу («секреты — никогда в настройки»).
2. **Аккаунт — только своё**: `tg_accounts` хранит название, телефон
   (обязателен: без него вход невозможен) и личную сессию (🔐,
   секрет уровня пароля — появляется после входа). Колонки
   `api_id`/`api_hash` удалены (миграция `d8f2a61c4e93`).
3. **Интерфейс**: ключ правится в «Настройки → Общие», блок
   «API Telegram» (hash показывается маской); диалог добавления
   аккаунта — только название и телефон. Вход и активация userbot
   берут пару из общей записи; без ключа — понятная ошибка,
   куда его вписать.
4. **Миграция без переноса данных**: разовая операция выполняется
   руками (шифртекст копируется как есть — ключ шифрования тот же),
   в коде миграции — только схема. Перед операцией — бэкап файла БД.

## Альтернативы

- **Пара в `app_settings` открытым текстом.** Меньше на одну таблицу,
  но ломает правило ADR-0009 и оставляет api_hash читаемым в любом
  бэкапе файла БД. Экономии почти нет (миграция колонок нужна всё
  равно). Отклонено.
- **Оставить пару у каждого аккаунта.** Гибкость «разные приложения
  для разных аккаунтов» никому не нужна (личный инструмент), а цена —
  повторный ввод и неверная модель данных. Отклонено.

## Последствия

- **Плюсы:** ключ вводится один раз; добавление аккаунта — два поля
  (название, телефон); сущности разведены по смыслу: приложение —
  ключ, аккаунт — телефон и сессия.
- **Минусы/риски:** сессии, созданные под другой парой, продолжают
  работать с общей (авторизация MTProto к api_id жёстко не привязана —
  проверено на практике переносом; при аномалиях достаточно повторного
  входа). Откат миграции возвращает колонки заглушками — после отката
  реквизиты нужно указать заново.
