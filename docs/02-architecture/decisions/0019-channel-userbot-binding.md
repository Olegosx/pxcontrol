# ADR-0019. Привязка userbot-аккаунта к каналу; пул клиентов MTProto

> Статус: accepted
> Дата: 2026-09-04 · Автор: olegosx
>
> Уточняет [ADR-0007](0007-hybrid-botapi-mtproto.md) (userbot),
> [ADR-0011](0011-publish-via-userbot.md) (публикация через userbot),
> [ADR-0017](0017-telegram-request-budget.md) (бюджет — на аккаунт)
> и [ADR-0018](0018-telegram-api-key-per-app.md) (общий ключ API).

## Контекст

У каналов могут быть разные userbot-админы, и постить в канал обязан
именно его админ — из своей сессии. Прежняя модель этого не выражала:
у канала был лишь булев флаг `userbot_admin` («какой-то userbot —
админ», без указания какой), а шлюз держал один клиент MTProto на всё
приложение — «первый по id аккаунт с сессией». Второй аккаунт был
мёртвым грузом: публикация в его каналы шла от чужого имени и падала
с «не администратор», а флаг врал по построению (его выставляла
проверка через случайно активный аккаунт).

Бот, в отличие от userbot, самостоятелен: Bot API работает по токену,
пользовательская сессия в его запросах не участвует, владелец нужен
только в BotFather (и это обычно личный аккаунт, которого в приложении
нет). Поэтому привязка «бот → аккаунт» не заводится — у канала
по-прежнему прямая ссылка `bot_id`.

## Решение

1. **Ссылка вместо флага.** `channels.userbot_admin: bool` →
   `channels.tg_account_id` — внешний ключ на `tg_accounts`,
   `ON DELETE SET NULL` (зеркально `bot_id`; миграция `e6b9d43a7f21`,
   только схема — привязка существующих каналов выполнена вручную).
   «Есть ли userbot-админ» выводится из привязки (`ChannelDto` отдаёт
   это свойством).
2. **Пул клиентов MTProto.** Шлюз держит словарь «id аккаунта →
   `MtprotoTransport`» (сам транспорт не изменился — экземпляров стало
   больше). При старте активируются все аккаунты с сессиями, отказ
   каждого изолирован. Userbot-операции адресные: `publish`,
   `get_scheduled`, `check_channel_userbot`, `userbot_premium` —
   с параметром `account_id`.
3. **Маршрутизация и лимиты — по привязке.** Публикация и чтение
   отложек канала идут через транспорт его аккаунта; лимит файла
   (2000/4000 МиБ) — по Premium именно этого аккаунта. Аккаунт при
   подключении канала выбирается явно (без авто-перебора: при двух
   админах-кандидатах он привязал бы случайного); на бот-пути
   и при перепроверке канала без привязки админ ищется опросом
   вошедших аккаунтов, привязывается первый подтверждённый.
4. **Перепроверка доступов** меняет привязку только по подтверждённому
   ответу Telegram: подтверждённый отказ привязанного аккаунта снимает
   привязку (иначе публикация падала бы), сбой сети — не трогает.
5. **Флуд-лимит — пер-аккаунтный** (развитие ADR-0017): дозор слотов
   очереди отправки при флуде прекращает опрос только каналов
   провинившегося аккаунта; каналы других аккаунтов проверяются дальше.
6. **Удаление аккаунта** гасит только его клиента; каналы отвязывает
   политика SET NULL, интерфейс перед удалением перечисляет каналы,
   которые останутся без userbot-админа (предупреждение, не запрет).

## Альтернативы

- **Один активный клиент с переключением на операцию.** Без новых
  сущностей, но переподключение на каждый пост, гонки очереди отправки
  между каналами разных аккаунтов и лишние окна недоступности.
  Отклонено.
- **Авто-перебор аккаунтов при подключении канала.** Меньше кликов,
  но при двух аккаунтах-админах одного канала привязка доставалась бы
  случайному. Отклонено в пользу явного выбора (авто-поиск остаётся
  только там, где выбора нет: попутная проверка бот-пути
  и перепроверка канала без привязки).

## Последствия

- **Плюсы:** несколько userbot-аккаунтов работают одновременно, каждый
  канал постит из сессии своего админа; Premium и флуд-лимиты честные,
  пер-аккаунтные; бюджет запросов (ADR-0017) распределяется по
  аккаунтам.
- **Минусы/риски:** больше одновременных MTProto-соединений (по числу
  вошедших аккаунтов — на личном масштабе единицы); эвристика Premium
  для рекомендации битрейта на «Видео» — «хоть один аккаунт
  с подпиской» (очередь обработки канала не знает; строгая проверка
  лимита остаётся за публикацией).
