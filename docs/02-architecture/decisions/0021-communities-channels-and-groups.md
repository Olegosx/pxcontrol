# ADR-0021. Сообщества: канал и группа — виды одной сущности

> Статус: accepted
> Дата: 2026-09-06 · Автор: olegosx
>
> Развивает [ADR-0007](0007-hybrid-botapi-mtproto.md) (гибрид транспортов),
> [ADR-0010](0010-posts-fire-and-forget.md) (истина — Telegram),
> [ADR-0011](0011-publish-via-userbot.md) (публикация через userbot),
> [ADR-0016](0016-persistent-publish-queue.md) (очередь и слоты отложек),
> [ADR-0019](0019-channel-userbot-binding.md) (привязка userbot-аккаунта).

## Контекст

Приложение подключает только каналы-вещалки. Проверки при подключении
(`check_channel` обоих транспортов) требуют «админ с правом публиковать»,
но тип сущности Telegram (канал это или группа) не смотрят. Отсюда два
дефекта: группа через бота отклоняется с вводящим в заблуждение текстом
«нет права публиковать» (права `can_post_messages` в группах не существует
в принципе), а группа, где userbot — создатель, проходит проверку
и подключается «как канал» — дыра в валидации, не задуманная возможность.

Продуктовое требование: группы (супергруппы) должны быть равноправной
целью публикации наравне с каналами — включая форумы (группы с темами).

Требование к имени сущности: канал/группа — не только цель публикации.
По дорожной карте следующий модуль — парсинг источников, и источником
будет та же сущность (чужой канал или группа, которые мы читаем). Имя
«канал» вводит в заблуждение уже сейчас, «цель» — введёт после появления
источников.

Предметные различия Telegram, которые обязано учесть решение:

- **Права.** В канале публикует админ с правом `post_messages`. В группе
  такого права нет: писать может любой участник, не ограниченный
  в отправке; боту достаточно быть участником.
- **Форумы.** Тема форума — отдельная лента; отправка в неё требует
  идентификатор темы (`message_thread_id` в Bot API, ответ на корневое
  сообщение темы в MTProto). Список тем умеет читать только userbot —
  в Bot API метода перечисления тем нет. Форумность — изменчивое
  свойство: владелец включает и выключает её на живой группе.
- **От чьего имени.** Пост в канале выходит от имени канала; пост
  в группе — от имени публикатора (userbot-аккаунта или бота).
- **Малые группы** (не супергруппы) — другой формат ID и модель
  участников; Telegram сам мигрирует их в супергруппы при включении
  ряда функций.
- **Отложенные записи** в группах работают тем же серверным механизмом
  и с тем же лимитом 100 на чат, что и в каналах (подтвердить живым
  прогоном на этапе тестов).

## Решение

1. **Единая сущность «сообщество» (`Community`)** — подключённый канал
   или группа Telegram. Обе роли — цель публикации сейчас, источник
   контента в будущем — покрываются одним именем. Хранение — одна
   таблица с видом, а не параллельные таблицы: вся инфраструктура
   (очередь отправки, пер-сообщественные настройки, шаблоны подписей,
   пресеты, «Расписание») продолжает работать по одному внешнему ключу.

2. **Переименование — отдельным подготовительным этапом** без изменения
   поведения: таблицы `channels` → `communities`, `channel_settings` →
   `community_settings` (колонка `channel_id` → `community_id`),
   `publish_queue_items.channel_id` → `community_id`; код — `Channel` →
   `Community`, `ChannelsService` → `CommunitiesService`, `ChannelDto` →
   `CommunityDto` и далее по цепочке; та же миграция обновляет хранимые
   строки имён ключей настроек, содержащие слово «channel»
   (`publish_last_channel_id` → `publish_last_community_id`). Поле
   `tg_chat_id` не переименовывается — это идентификатор чата
   в терминах Telegram, имя верное. Автокопия БД перед миграцией
   уже штатная.

3. **Вид сообщества** — колонка `kind` (`channel` | `group`),
   определяется при подключении по сущности из API (тип чата у Bot API;
   флаги «вещалка/супергруппа» у Telethon) и не меняется жизнью записи.
   Малые группы отклоняются при подключении с подсказкой «преобразуйте
   группу в супергруппу». Существующие строки при миграции получают
   `kind = channel` (валидация раньше пропускала только каналы; редкие
   просочившиеся группы владелец переподключит).

4. **Проверки прав — видозависимые**, парно в обоих транспортах:
   - канал: как сейчас — админ (или создатель) с правом публиковать;
   - группа + userbot: аккаунт — участник, не ограниченный в отправке
     сообщений (точный набор флагов Telethon уточняется по документации
     при реализации);
   - группа + бот: бот — участник группы, админство не требуется.
   Тексты ошибок — тоже видозависимые (сегодняшнее «нет права
   публиковать в канале» для группы — дезинформация).

5. **Форумы.** Признак — булева колонка `forum`, обновляется при
   подключении и перепроверке доступов (изменчивое свойство — не третий
   `kind`). Темы в БД не хранятся: список читается из Telegram живьём
   (истина — Telegram, принцип ADR-0010). Черновик `PostDraft` получает
   необязательный `topic_id`; таблица `publish_queue_items` — колонку
   под него (элемент очереди переживает перезапуск и обязан помнить
   тему). Выбор темы доступен сообществам с userbot; форум только
   с ботом публикует в общую ленту (ограничение Bot API — перечислять
   темы нечем), с пояснением в интерфейсе. Без выбранной темы пост
   идёт в общую ленту.

6. **Матрица возможностей публикации не меняется по форме** (ADR-0011):
   userbot — полный путь (любые типы, до 2000/4000 МиБ, отложенные),
   бот — запасной («сейчас», до 50 МБ). Слоты отложек и очередь
   (ADR-0016) действуют для групп без изменений — лимит Telegram
   тот же, 100 на чат.

7. **Интерфейс** — единая страница «Каналы и группы»: один список со
   значком вида и фильтром, общий диалог подключения. Отдельной
   страницы для групп нет — все действия идентичны.

## Альтернативы

- **Отдельная таблица и сервис для групп.** Буквальная «отдельность»,
  но каждый потребитель (очередь, настройки, подписи, «Расписание»,
  страницы) должен учиться работать с двумя источниками; внешние ключи
  двоятся. Дублирование в чистом виде. Отклонено.
- **Оставить имя `channels`, добавив `kind`.** Минимальный дифф, но имя
  таблицы и классов лжёт о содержимом — равноправие групп остаётся
  декларацией, каждый читатель кода будет рассуждать «это про каналы».
  Отклонено.
- **Другие имена сущности.** `Chat` — коллизия с полем `tg_chat_id`
  (наш ключ против телеграмного — двусмысленность «chat_id»);
  `Peer` — коллизия с `_peer_id` в `mtproto.py` (числовой ID Telegram);
  `Target`/`Destination` — не годятся будущему источнику парсинга;
  `Node` — нейтрально, но безлико. Выбрано `Community` («сообщество»):
  покрывает канал и группу (прецедент — «сообщества» ВКонтакте),
  осмысленно в обеих ролях.
- **Отклонять группы совсем** («честно закрыть дверь» проверкой вида).
  Дёшево, закрыло бы дыру валидации, но противоречит продуктовому
  требованию. Отклонено.
- **Поддержать группы без форумов.** Меньший объём, но темы — часть
  модели групп Telegram: «группы без тем» повторили бы сегодняшнюю
  ошибку («каналы без групп») этажом ниже. Отклонено.

## Последствия

- **Плюсы:** группы и форумы — полноправные сообщества во всей
  инфраструктуре без её переделки (очередь, настройки, подписи,
  расписание работают по `community_id` как работали); дыра валидации
  закрыта видозависимыми проверками; честные тексты ошибок; имя
  сущности готово к модулю источников.
- **Минусы / риски:** большой механический дифф этапа переименования
  (~15 файлов; компенсация — этап отделён от поведенческих правок,
  строгий mypy не даёт пропустить точку использования); пост в группу
  выходит от имени публикатора, не от имени группы — зафиксировать
  в документации, чтобы не было сюрприза; список тем недоступен
  бот-пути (ограничение Bot API); отложки в темах — подтвердить живым
  прогоном.
- **Что нужно сделать дальше:**
  1. этап 0 — переименование (миграция + код + тесты + документация,
     поведение не меняется);
  2. этап 1 — `kind` и `forum`, видозависимые проверки прав, отказ
     малым группам;
  3. этап 2 — сервисы и очередь: `kind` в DTO, `topic_id` в черновике
     и таблице очереди;
  4. этап 3 — интерфейс: «Каналы и группы», значок вида, выбор темы;
  5. этап 4 — тесты (матрица «вид × транспорт × роль», миграции, живой
     прогон отложки в группе и теме) и документация (глоссарий,
     `channels.md` → `communities.md`, модель данных, CLAUDE.md).
