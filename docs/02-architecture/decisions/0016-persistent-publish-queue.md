# ADR-0016. Персистентная очередь отправки со слотами отложек

> Статус: accepted
> Дата: 2026-08-26 · Автор: olegosx
>
> Замещает [ADR-0012](0012-publish-queue-in-memory.md) (очередь
> в памяти); уточняет [ADR-0010](0010-posts-fire-and-forget.md)
> и [ADR-0015](0015-batch-publishing.md).

## Контекст

Telegram жёстко ограничивает отложенные сообщения: **не больше 100
на чат/канал** (Premium лимит не увеличивает — он даёт лишь
повторяющиеся отложки), горизонт — до года вперёд, момент менее чем
за 10 секунд публикуется сразу. Превышение — ошибка API
`SCHEDULE_TOO_MUCH`. Проверено 2026-08-26:
[limits.tginfo.me](https://limits.tginfo.me/en),
[core.telegram.org/api/scheduled-messages](https://core.telegram.org/api/scheduled-messages).

Нужно планировать в канал больше 100 постов. Значит, часть постов
обязана ждать на нашей стороне, переживая перезапуск приложения, —
очередь в памяти (ADR-0012) этого не умеет. ADR-0012 сам предусматривал
возврат к персистентности «при реальной нужде» — она наступила.

## Решение

Отдельной «очереди ожидания» не заводится — расширяется существующая
очередь отправки (`PublishQueue`): есть слот — пост уходит, нет — ждёт
в той же очереди.

1. **Очередь хранится в SQLite** (таблица `publish_queue_items`:
   поля черновика + статус + ошибка). При старте движка очередь
   наполняется из таблицы; элемент, отправлявшийся в момент падения,
   возвращается в ожидающие. Завершённые (отправлен/отменён) из таблицы
   удаляются — истина по вышедшим постам остаётся каналом (ADR-0010:
   сервер Telegram публикует ближайшие ≤100 и без нас).
2. **Новое состояние «ждёт слота» (WAITING).** Отложенный черновик
   при постановке встаёт в WAITING; пост «сейчас» слота не занимает
   и не ждёт никогда. Проверка слотов: сразу после постановки
   и далее раз в N минут (настройка `QUEUE_SLOT_POLL_MINUTES`,
   по умолчанию 5). Свободно = 100 − фактические отложки канала
   (чтение с сервера) − уже выпущенные, но ещё не отправленные
   отложенные этого канала. Освободилось — в отправку переходят
   элементы с **самой ближайшей датой публикации** (внутри канала);
   полный канал не блокирует посты в другие каналы.
3. **Просроченное время — публикация «сейчас».** Если желаемый момент
   уже прошёл (или ближе минуты), элемент перестаёт быть отложкой:
   слота не требует, публикуется как обычное сообщение. Правило
   действует на всех путях, включая «Повторить» у элемента в ошибке
   (типовой случай: пост упал ночью, повтор утром) — просроченное
   время при повторе снимается (уточнено 2026-08-26).
4. **Заполнение — до всех 100.** Гонка с ручными отложками из клиента
   Telegram обрабатывается: `SCHEDULE_TOO_MUCH` тихо возвращает элемент
   в «ждёт слота» (не в ошибку).
5. **Папка очереди на диске.** Жизненный цикл поста зеркалится
   папками: `processed` (готово) → `queued` (в очереди) → `published`
   (отправлено), с сохранением внутренней структуры. Постановка
   переносит файл (и кадр-превью) из результатов в папку очереди —
   его нельзя случайно удалить со страницы «Готовых видео» и поставить
   повторно; отмена/снятие без отправки возвращает файл в результаты;
   успешная отправка переносит в опубликованные. Переносятся только
   файлы из-под корня результатов — произвольные вложения с диска
   не трогаются. Жизненный цикл определён только для видео: не-видео
   из папки результатов (кадр-превью как «Фото», ролик как «Документ»)
   в постановке отклоняется с понятной ошибкой — такой файл
   принадлежит конвейеру обработки, для отправки его копируют
   в другое место (уточнено 2026-08-26). Коллизия имён в папке
   очереди — понятная ошибка постановки.
6. **Интерфейс.** Панель очереди на «Публикации» показывает
   отправляющиеся/ожидающие как раньше; карточек — не больше 20
   (ближайшие по дате) плюс сводка «ждут слота: N». Полный просмотр —
   кнопка «Вся очередь…»: живой диалог со всеми элементами, сортировка
   (ближайшие / порядок постановки / по каналам) и фильтры (статус,
   канал); действия у карточек те же (реализован 2026-08-26).
7. **Честное ограничение** (фиксируется здесь и в подписи карточек):
   ждущие слота публикуются только при запущенном приложении. Первые
   ~100 отложек выпустит сервер Telegram даже без нас; хвосту нужен
   работающий pXcontrol.

## Альтернативы

- **Отдельная таблица-накопитель + перекладка в очередь памяти.**
  Те же данные, но две сущности, два интерфейса и перекладочный
  механизм между ними. Отклонено: ждущий элемент — это состояние
  элемента одной очереди, а не отдельная очередь.
- **Полностью локальное планирование (всё публикует приложение
  «сейчас» по расписанию).** Теряется главное свойство ADR-0010 —
  ближайшие посты выходят даже при выключенном приложении. Отклонено.
- **Держать запас слотов (заполнять до 95).** Не нужно: фактическое
  число отложек перечитывается с сервера, гонка закрыта обработкой
  `SCHEDULE_TOO_MUCH`.

## Последствия

- **Плюсы:** планирование сотен постов; очередь переживает перезапуск;
  файлы ожидающих постов защищены папкой очереди; одна очередь — один
  интерфейс и одна модель в голове пользователя.
- **Минусы/риски:** хвост очереди зависит от запущенного приложения;
  локальная таблица постов возвращается (ограниченно: только ещё
  не отправленное; вышедшее — по-прежнему истина канала); порядок
  выпуска внутри канала — по дате публикации, не FIFO.
- Удаление канала каскадом удаляет его элементы очереди; их файлы
  остаются в папке очереди (не теряются, но требуют ручного разбора) —
  известное упрощение.
