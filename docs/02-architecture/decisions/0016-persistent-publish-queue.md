# ADR-0016. Персистентная очередь отправки со слотами отложек

> Статус: accepted
> Дата: 2026-08-26 · Автор: olegosx
>
> Замещает [ADR-0012](0012-publish-queue-in-memory.md) (очередь
> в памяти); уточняет [ADR-0010](0010-posts-fire-and-forget.md)
> и [ADR-0015](0015-batch-publishing.md).

## Контекст

Telegram жёстко ограничивает отложенные сообщения: **не больше 100
на чат/канал** (Premium лимит не увеличивает — он даёт лишь
повторяющиеся отложки), горизонт — до года вперёд, момент менее чем
за 10 секунд публикуется сразу. Превышение — ошибка API
`SCHEDULE_TOO_MUCH`. Проверено 2026-08-26:
[limits.tginfo.me](https://limits.tginfo.me/en),
[core.telegram.org/api/scheduled-messages](https://core.telegram.org/api/scheduled-messages).

Нужно планировать в канал больше 100 постов. Значит, часть постов
обязана ждать на нашей стороне, переживая перезапуск приложения, —
очередь в памяти (ADR-0012) этого не умеет. ADR-0012 сам предусматривал
возврат к персистентности «при реальной нужде» — она наступила.

## Решение

Отдельной «очереди ожидания» не заводится — расширяется существующая
очередь отправки (`PublishQueue`): есть слот — пост уходит, нет — ждёт
в той же очереди.

1. **Очередь хранится в SQLite** (таблица `publish_queue_items`:
   поля черновика + статус + ошибка). При старте движка очередь
   наполняется из таблицы; элемент, отправлявшийся в момент падения,
   возвращается в ожидающие. Завершённые (отправлен/отменён) из таблицы
   удаляются — истина по вышедшим постам остаётся каналом (ADR-0010:
   сервер Telegram публикует ближайшие ≤100 и без нас).
2. **Новое состояние «ждёт слота» (WAITING).** Отложенный черновик
   при постановке встаёт в WAITING; пост «сейчас» слота не занимает
   и не ждёт никогда. Проверка слотов: сразу после постановки
   и далее раз в N минут (настройка `QUEUE_SLOT_POLL_MINUTES`,
   по умолчанию 5). Свободно = 100 − фактические отложки канала
   (чтение с сервера) − уже выпущенные, но ещё не отправленные
   отложенные этого канала. Освободилось — в отправку переходят
   элементы с **самой ближайшей датой публикации** (внутри канала);
   полный канал не блокирует посты в другие каналы.
3. **Просроченное время — публикация «сейчас».** Если желаемый момент
   уже прошёл (или ближе минуты), элемент перестаёт быть отложкой:
   слота не требует, публикуется как обычное сообщение. Правило
   действует на всех путях, включая «Повторить» у элемента в ошибке
   (типовой случай: пост упал ночью, повтор утром) — просроченное
   время при повторе снимается (уточнено 2026-08-26). Догон щадящий
   (уточнено 2026-08-27): между догоняющими постами очередь держит
   паузу `CATCHUP_INTERVAL_S` (30 с) — после простоя канал «оживает»,
   а не строчит залпом; флуд-лимит Telegram («подождите N секунд»,
   общий класс `TelegramFloodError`) — не ошибка элемента: очередь
   ждёт названный срок и повторяет, карточка на время паузы получает
   пометку.
4. **Заполнение — до всех 100.** Гонка с ручными отложками из клиента
   Telegram обрабатывается: `SCHEDULE_TOO_MUCH` тихо возвращает элемент
   в «ждёт слота» (не в ошибку).
5. **Папка очереди на диске.** Жизненный цикл поста зеркалится
   папками: `processed` (готово) → `queued` (в очереди) → `published`
   (отправлено), с сохранением внутренней структуры. Постановка
   переносит файл (и кадр-превью) из результатов в папку очереди —
   его нельзя случайно удалить со страницы «Готовых видео» и поставить
   повторно; отмена/снятие без отправки возвращает файл в результаты;
   успешная отправка переносит в опубликованные. Переносятся только
   файлы из-под корня результатов — произвольные вложения с диска
   не трогаются. Жизненный цикл определён только для видео: не-видео
   из папки результатов (кадр-превью как «Фото», ролик как «Документ»)
   в постановке отклоняется с понятной ошибкой — такой файл
   принадлежит конвейеру обработки, для отправки его копируют
   в другое место (уточнено 2026-08-26). Коллизия имён в папке
   очереди — понятная ошибка постановки. Пока в очереди есть посты
   (включая ошибки — их файлы нужны повтору), путь папки очереди
   менять нельзя: операции жизненного цикла узнают файлы по текущему
   пути, смена молча бросила бы файлы в старой папке; «Настройки»
   сохраняют папки через охраняемую точку `Engine.update_video_folders`
   (уточнено 2026-09-05).

   **Уборка опустевших папок** (добавлено 2026-09-05). Пакетные
   подпапки, из которых ушёл последний файл, удаляются — но только
   когда очередь по папке полностью отработана: пока элементы очереди
   живы, отмена может вернуть файлы в результаты. Признак «очередь
   по папке отработана» — физический и следует из зеркальности путей:
   *зеркало папки в дереве очереди пусто или отсутствует* (файлы
   ждущих и ошибочных элементов лежат в папке очереди физически).
   Этот инвариант — часть контракта решения: посторонние файлы
   в папке очереди блокируют уборку её зеркала. Правила по точкам:
   - постановка (`processed → queued`) не убирает ничего — опустевшая
     папка результатов ждёт возможного возврата;
   - уход файла из папки очереди (публикация, возврат при отмене)
     убирает её опустевшие папки, затем — их опустевшие зеркала
     в результатах (возвращаться больше нечему);
   - удаление результата корзинкой и публикация мимо очереди убирают
     уровень результатов, только если его зеркало в очереди пусто
     или отсутствует;
   - папка опубликованных не убирается (файлы туда только приходят);
     корни деревьев не удаляются никогда.
   Гонки закрывает атомарность `rmdir` (непустую папку не удалит),
   обработка пересоздаёт свою папку перед записью (`mkdir`). При
   старте движка — разовая уборка: пустые папки дерева очереди
   (по инварианту они не принадлежат ни одному элементу) и их
   опустевшие зеркала; сама папка результатов не метётся — пустые
   подпапки там законны (рабочие папки пресетов, свои папки
   пользователя).
6. **Интерфейс.** Панель очереди на «Публикации» показывает
   отправляющиеся/ожидающие как раньше; карточек — не больше 20
   (ближайшие по дате) плюс сводка «ждут слота: N». Полный просмотр —
   кнопка «Вся очередь…»: живой диалог со всеми элементами, сортировка
   (ближайшие / порядок постановки / по каналам) и фильтры (статус,
   канал); действия у карточек те же (реализован 2026-08-26).
   У поста с вложением карточка даёт посмотреть файл системным
   приложением — той же кнопкой, что у карточек файлов на «Видео»
   и в пакете (добавлено 2026-09-11): пока пост ждёт отправки, его
   файл лежит в папке очереди, и это единственный способ увидеть,
   что именно уйдёт.
   **Шапка карточки начинается с логотипа сообщества и цветной метки
   слота** — времени публикации, «[18:00]» или «[сейчас]» (добавлено
   2026-09-12). В очереди из сотен постов это два первых вопроса —
   «куда» и «когда»; цвет метки выводится из самого времени, поэтому
   посты одного слота узнаются пачкой, одинаково во всех каналах
   и после перезапуска. Аватар берётся из кэша статистики сообществ,
   без него рисуется буква названия на цветной подложке. Слот — ещё
   и фильтр полного просмотра, рядом с фильтрами статуса и сообщества.
   Кнопки «Закрыть» у окна очереди нет намеренно: системный крестик
   и Esc закрывают его и так, а отдельная строка съедала высоту списка.
   **Страницами по 50** (добавлено 2026-09-11): очередь — это хвост
   сверх сотни отложек на канал, и показ всей разом перестраивал бы
   сотни карточек при каждой смене состава. Порядок обработки —
   фильтр → сортировка → срез страницы, поэтому сортировка остаётся
   сквозной по всей очереди. Номер страницы зажимается в существующие
   границы, а не отвергается: очередь живая, и страница исчезает
   под пользователем, когда посты уходят.
7. **Правка элемента** (добавлено 2026-09-11). Пост, который ещё
   не ушёл в Telegram, правится **прямо в своей карточке**: она
   раскрывается кликом, и внутри — форма (текст, вложение: замена,
   удаление, добавление; переименование при отправке, тема форума
   и время публикации). Жест тот же, каким раскрываются параметры
   файла на «Видео»; отдельного окна правки нет — оно было
   и заменено формой в карточке 2026-09-11, чтобы правка шла
   там же, где виден список. Правила:
   - **Что правится.** Статусы `pending`, `waiting` и `error` —
     всё, что ещё не ушло. Отправляющийся не правится (файл уже
     грузится — сначала «Отмена»). Ошибка в числе правимых намеренно:
     для очереди это живой элемент, ждущий вмешательства, а не
     завершённый исход — `finished()` здесь не годится (набор правимых
     статусов — `EDITABLE_STATUSES`; «покинул очередь» — признак
     `JobStatus.left_queue()`, см. дополнение о переезде на каркас).
   - **Канал-получатель не меняется.** У другого канала свои темы,
     свой лимит файла (Premium привязанного аккаунта) и своё право
     на отложенную публикацию; такой пост создают заново. Попытка
     подменить канал отклоняется движком, а не только интерфейсом.
   - **Замок от гонки с отправкой.** Перед первым ожиданием элемент
     помечается `editing`, и рабочий цикл его пропускает. Это надёжно
     потому, что цикл выбирает элемент и ставит ему `sending` без
     единой точки приостановки: помеченный он уже не подхватит. Дозор
     слотов такой элемент тоже не выпускает — статус ему поставит
     сама правка, по новому времени.
   - **Файлы** ездят по правилам п. 5: новое вложение из папки
     результатов переносится в папку очереди, прежнее возвращается
     в результаты. Сбой на любом шаге откатывает перенос. Тип файла
     конвейера сменить нельзя (ролик нельзя сохранить «Фото» или
     «Файлом»): маршрут `processed → queued → published` определён
     только для видео, иначе файл остался бы в папке очереди навсегда
     и блокировал уборку её папок.
   - **Исход правки — возврат в работу.** Статус пересчитывается
     по времени («сейчас» — в отправку, отложенное — ждать слота,
     просроченное снимается как при повторе), текст прошлой ошибки
     стирается: иначе на карточке висела бы неправда.
   - **Список остаётся живым во время правки.** Панель обновляет
     карточки точечно (`plan_cards`): меняется только то, что
     изменилось, а карточка с открытой формой не пересоздаётся.
     Прежняя пересборка всего списка при любом изменении убивала бы
     форму вместе с набранным текстом, стоило соседнему посту
     сменить статус. Если правимый элемент всё же покидает очередь
     (отправился, отменён, канал удалён), карточка исчезает,
     а человеку говорится, что незаконченная правка не сохранена.
   - Правка **уже созданных на сервере Telegram отложек** сюда
     не относится — это записи канала (ADR-0010), а не элементы
     очереди; их правка потребует обращения к Telegram и решается
     отдельно.
8. **Честное ограничение** (фиксируется здесь): ждущие слота
   публикуются только при запущенном приложении. Первые ~100 отложек
   выпустит сервер Telegram даже без нас; хвосту нужен работающий
   pXcontrol. В подписи карточек это сообщение было и убрано
   2026-09-12: одинаковая приписка в каждой строке списка — шум,
   а не информация; статус «ждёт слота отложек» остался.

## Дополнение (2026-09-12, переезд на общий каркас заданий)

Жизненный цикл элементов очереди (статусы, последовательный воркер,
прогресс, отмена, остановка) переехал в общий каркас
[ADR-0025](0025-job-queue-framework.md); всё предметное осталось здесь:
персистентность, слоты отложек, папка очереди, правка элемента,
щадящий догон. Поведение не изменилось — тесты очереди прошли миграцию
без правок по смыслу. Границу «что можно рвать отменой» очередь держит
сама: отменяется только задача передачи, подготовка с её запросами
к БД — никогда (ADR-0020).

## Альтернативы

- **Отдельная таблица-накопитель + перекладка в очередь памяти.**
  Те же данные, но две сущности, два интерфейса и перекладочный
  механизм между ними. Отклонено: ждущий элемент — это состояние
  элемента одной очереди, а не отдельная очередь.
- **Полностью локальное планирование (всё публикует приложение
  «сейчас» по расписанию).** Теряется главное свойство ADR-0010 —
  ближайшие посты выходят даже при выключенном приложении. Отклонено.
- **Держать запас слотов (заполнять до 95).** Не нужно: фактическое
  число отложек перечитывается с сервера, гонка закрыта обработкой
  `SCHEDULE_TOO_MUCH`.

## Последствия

- **Плюсы:** планирование сотен постов; очередь переживает перезапуск;
  файлы ожидающих постов защищены папкой очереди; одна очередь — один
  интерфейс и одна модель в голове пользователя.
- **Минусы/риски:** хвост очереди зависит от запущенного приложения;
  локальная таблица постов возвращается (ограниченно: только ещё
  не отправленное; вышедшее — по-прежнему истина канала); порядок
  выпуска внутри канала — по дате публикации, не FIFO.
- Правка элемента (п. 7) реализована 2026-09-11: движок —
  `PublishQueue.get_draft` / `PublishQueue.edit`, интерфейс — форма
  в раскрытой карточке (`QueueItemEditor`), одинаково на «Публикации»
  и в окне «Вся очередь…»; правимость решает общий набор статусов
  `EDITABLE_STATUSES` — одно правило на движок и интерфейс.
- Удаление канала снимает его элементы из живой очереди как «Отмену»
  (файлы возвращаются в результаты, активная отправка обрывается),
  затем каскад БД подчищает строки; связка — методом движка
  `Engine.delete_channel` (упрощение с осиротевшими файлами закрыто
  2026-08-26).
