# ADR-0040. Задача «Приём заявок»: одобрение заявок на вступление с правилами

> Статус: accepted — реализовано; читающие шаги пробы прошли 2026-09-22, одобрение с ограничением ждёт настоящей заявки
> Дата: 2026-09-22 · Автор: olegosx
>
> Второй новый вид задач на основании [ADR-0038](0038-community-tasks.md);
> опирается на [ADR-0035](0035-community-executors-and-rights.md)
> (снимок прав, ввод исполнителя по заявке — статус «заявка
> отправлена» с другой стороны той же двери), [ADR-0036](0036-executor-dispatch-and-urgency.md),
> [ADR-0024](0024-telegram-account-lane.md) и [ADR-0026](0026-community-maintenance.md)
> (границы массовой работы; «отказ — пропуск, флуд — конец прохода»;
> урок о хеше доступа).

## Контекст

Требование владельца (21.09.2026): задача приёма участников
в сообщество, куда попадают по заявке. Опции: отклонение удалённых
аккаунтов; приём с полным ограничением прав, если в профиле есть
ссылки (актуально для групп). Уточнение 21.09.2026: «ссылки
в профиле» — два отдельных флажка: описание профиля (био) и канал
в профиле.

### Что об этом говорит Telegram

Сверено 21.09.2026 по core.telegram.org и установленной Telethon 1.44.0;
помеченное «проверить живьём» проверяет проба `_misc/tg_join_requests_probe.py`.

- **Список ожидающих** — только пользовательским аккаунтом:
  [`messages.getChatInviteImporters`](https://core.telegram.org/method/messages.getChatInviteImporters)
  с флагом `requested`, страницами со смещением «дата + заявитель».
  В ответе — `importers` (`chatInviteImporter`: `user_id`, `date`,
  `about` — «for users with pending requests, contains bio of the
  user») и `users` с хешами доступа. У Bot API метода перечисления нет:
  боту заявки приходят только событием.
- **Решение** — [`messages.hideChatJoinRequest`](https://core.telegram.org/method/messages.hideChatJoinRequest)
  с `approved`; ошибки `HIDE_REQUESTER_MISSING` (заявки уже нет),
  `USER_ALREADY_PARTICIPANT`, `INPUT_USER_DEACTIVATED` (аккаунт удалён),
  `USER_CHANNELS_TOO_MUCH`, `CHAT_ADMIN_REQUIRED`.
- **Право.** На странице [приглашений](https://core.telegram.org/api/invites)
  сказано лишь «administrators can then use hideChatJoinRequest»;
  флаг `chatAdminRights` словами не назван. Bot API для тех же
  операций требует `can_invite_users` — принято рабочей гипотезой
  (`ExecutorAction.APPROVE_REQUESTS` = администратор с `invite_users`),
  *проверить живьём*.
- **Удалённость** — `user.deleted` («whether the account of this user
  was deleted»); **канал в профиле** — `userFull.personal_channel_id`
  ([конструктор](https://core.telegram.org/constructor/userFull)) через
  `users.getFullUser`: один запрос на заявителя.
- **Ограничение** — [`channels.editBanned`](https://core.telegram.org/method/channels.editBanned)
  с [`chatBannedRights`](https://core.telegram.org/constructor/chatBannedRights):
  выставленный флаг **запрещает**; `view_messages` — это бан, его
  не ставим; `until_date` пустой — бессрочно. Обёртка Telethon
  `edit_permissions` не знает гранулярных прав 2023 года — запрос
  собирается прямо. Применимость к ещё не участнику не документирована —
  порядок «одобрить, затем ограничить», *проверить живьём*.
- **Событие** `updatePendingJoinRequests` для пользователей несёт
  только счётчик и последних заявителей — без списка.

## Решение

1. **Вид задачи `JoinRequestsTask`** (`engine/tasks/join_requests.py`)
   на контракте ADR-0038: параметры — отклонять удалённых (умолчание
   да), ограничивать при ссылке в описании профиля, ограничивать при
   канале в профиле, потолок за проход (умолчание 50, минимум 1).
   Курсор не нужен: каждый проход читает ожидающие с начала — разобранные
   из списка исчезают.
2. **Решение по заявке** — по порядку: аккаунт удалён → отклонить
   (или оставить, если флажок снят); иначе одобрить; затем — только
   в **группе** и только при включённом правиле — если в профиле
   ссылки, наложить полное ограничение. В канале ограничить участника
   нечем: флажки неактивны с объяснением, заявки принимаются как есть.
3. **Ссылка в описании** — чистая `profile_has_links(bio)`: адрес,
   `t.me`, домен с распространённой зоной, `@упоминание`. Описание
   приходит бесплатно вместе с заявкой; **канал в профиле** стоит
   одного запроса на заявителя и потому включается отдельным флажком
   (форма говорит о цене).
4. **Порядок «одобрить, затем ограничить»** — потому что применимость
   ограничения к ещё не участнику не документирована; ограничение
   бессрочное. Одобряет и ограничивает **один** исполнитель: с правом
   приглашать, а при включённом ограничении — ещё и с правом исключать
   (`choose_executor` вида); никого такого — отказ при постановке
   с объяснением.
5. **Границы и отказы** (ADR-0026): потолок за проход; отказ по одной
   заявке (`UserbotJoinRequestError`: заявки уже нет, заявитель негоден)
   — пропуск с записью в журнал; флуд-лимит — конец прохода. Запуск
   «без изменений» читает заявки и считает решения, не трогая Telegram
   (кроме чтения профиля, если включено).
6. **Граница шлюза**: `JoinRequest` (id, хеш доступа, дата, био,
   удалён, подпись) и `JoinRequestsPage`; транспорт `join_requests_page`
   (первая страница — пустое смещение: `offset_date` 0
   и `inputUserEmpty`; хеши заявителей запоминаются на время запуска
   для адресации следующей страницы), `handle_join_request`,
   `restrict_fully`, `has_personal_channel`. Обёртки шлюза — приоритет
   `MAINTENANCE`.
7. **Только userbot и только опросом.** Bot API не перечисляет
   ожидающие заявки; обработка потока обновлений Telethon
   в приложении не заведена ни для чего, а событие всё равно не несёт
   списка. Расписание задачи (например, каждые 10 минут) даёт тот же
   результат без второго механизма.
8. **Интерфейс** — раздел «Приём заявок»: три флажка, потолок,
   «Посмотреть заявки» и «Разобрать заявки» (с подтверждением: правила
   словами, потолок, необратимость), расписание с подтверждением
   при включении, журнал.

## Альтернативы

- **Массовое `hideAllChatJoinRequests`.** Одним запросом, но без правил
  по заявителю — ни отклонить удалённых, ни ограничить по ссылкам.
  Отклонено.
- **Событие `updatePendingJoinRequests` вместо опроса.** Потребовало бы
  обработки потока обновлений, которой нет, и всё равно не даёт
  списка. Отклонено (п. 7).
- **Через бота** (`approveChatJoinRequest`, `restrictChatMember`).
  Список заявок бот получить не может — только событием, которое
  нужно ловить постоянно. Отклонено; userbot — единственный
  и простейший маршрут.
- **Отклонять заявителей со ссылками вместо ограничения.** Проще,
  но требование — принять с ограничением: в группе такой участник
  читает, но не пишет. Отклонено.
- **Проверять канал в профиле всегда.** Точнее, но запрос на каждого
  заявителя; правило включается флажком с названной ценой. Отклонено
  как умолчание.

## Последствия

- **Плюсы:** вид ложится на контракт ADR-0038 без правок сервиса;
  правило «ссылка в профиле» — чистая функция с тестами; хеш доступа
  едет вместе с заявкой (урок ADR-0026 применён заранее); в канале
  форма не обещает того, чего Telegram не даст.
- **Минусы / риски:** три утверждения о Telegram не подтверждены
  документацией словами (форма первой страницы, право `invite_users`,
  ограничение сразу после одобрения) — до пробы поведение на них
  считается предположением; распознавание ссылок эвристично (список
  зон конечен) — ложные срабатывания ограничивают, а не отклоняют,
  и это обратимо администратором; одобрение по расписанию — массовая
  операция с пользовательского аккаунта, сдерживают потолок и интервал.
- **Что нужно сделать дальше:** шаг `approve-one` пробы — когда
  в тестовой группе появится настоящая заявка с постороннего аккаунта
  (проверит поле `about` и ограничение сразу после одобрения);
  по итогу при необходимости поправить порядок ограничения.

## Дополнение (2026-09-22, живая проба — читающие шаги)

Проба `_misc/tg_join_requests_probe.py` (шаги `list`, `rights`,
`preview`; протокол — `_misc/tg_join_requests_probe_results.txt`):

1. **Первая страница с пустым смещением** (`offset_date` 0
   и `inputUserEmpty`) сервер принимает — в обоих тестовых сообществах
   ответ пришёл без ошибки (заявок 0). Утверждение о форме первой
   страницы подтверждено.
2. **Право на заявки** совпало с правилом `can(…, APPROVE_REQUESTS)`
   у обоих исполнителей пула в обоих сообществах: администратор
   с правом приглашать видит, участник без прав получает
   `CHAT_ADMIN_REQUIRED`. Гипотеза «то же право, что у Bot API»
   не опровергнута.
3. **Просмотр задачей** отработал за 0,3 с с честным «заявок нет»
   в журнале.

Не проверено — заявок в тестовых сообществах не было: приходит ли
`about` вместе с заявкой и принимает ли сервер полное ограничение
сразу после одобрения. Это шаг `approve-one`, он требует настоящей
заявки с постороннего аккаунта. Побочное наблюдение: отказ
`CHAT_ADMIN_REQUIRED` переводится общим текстом про «право
публиковать» — для заявок точнее было бы «право приглашать»; текст
общий на все операции, и менять его ради одного случая не стали.
