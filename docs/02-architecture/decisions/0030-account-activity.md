# ADR-0030. Учёт активности пользователей и ботов: боты на дорожках, запись на операцию

> Статус: accepted
> Дата: 2026-09-15 · Автор: olegosx
>
> Опирается на [ADR-0024](0024-telegram-account-lane.md) (дорожка аккаунта —
> единственный путь к Telegram), [ADR-0029](0029-users-and-bots-section.md)
> (раздел «Пользователи и боты», где активность показывается)
> и [ADR-0020](0020-cooperative-background-shutdown.md) (кооперативная
> остановка фоновых задач).

## Контекст

У пользователя (userbot-аккаунта) и бота появилась карточка (ADR-0029),
но она молчит о главном: как сильно приложение нагружает исполнителя.
Между тем нагрузка — вопрос выживания аккаунта: Telegram ограничивает
именно аккаунт, флуд-лимит назначается ему целиком (ADR-0024), а этап 2
(источники) добавит долгие фоновые чтения тем же аккаунтам. Без учёта
человек узнаёт о перегрузке по факту — из отказов.

Два измерения, названные владельцем: **сколько** операций и **как долго**
они занимали исполнителя. Плюс исходы — ошибки и флуд-лимиты.

Обстоятельства:

- Все userbot-операции идут через дорожку аккаунта — другого пути нет
  (ADR-0024), поэтому счётчик в дорожке полон по построению. Бот-путь
  дорожкой не покрывался: восемь вызовов в четырёх сервисах шли в Bot API
  напрямую по токену, и отказ «подождите N секунд» у бота никого не
  останавливал — следующий вызов шёл как ни в чём не бывало.
- Операция может длиться дольше часа (загрузка файла) и пересекать
  границы часов. Почасовые корзины потребовали бы дробить интервал при
  записи или приписывать всё время часу окончания — костыль.
- Объём: при десятке сообществ опрос ботом даёт около тысячи обращений
  в сутки, userbot — сотни, публикации и обслуживание — десятки (проход
  обслуживания — 20 чтений истории, до 5 пачек удаления, до 20
  исключений). Порядка двух тысяч строк в сутки, ~100 байт строка,
  70 МБ в год. Для SQLite это ничто.

## Решение

1. **Боты тоже на дорожках.** Пул дорожек шлюза ключуется владельцем
   (`LaneOwner`: вид — пользователь или бот, и id). Дорожка бота —
   без зазора между запросами (`BOT_MIN_INTERVAL_S` = 0: лимиты Bot API
   щедрые и пер-бот), но с очередью, приоритетом и **заморозкой** после
   `RetryAfter` — как у пользователя. Бот-методы шлюза принимают
   `BotRef` (id + токен, токен исключён из `repr`); единственная операция
   без дорожки — проверка токена при добавлении: бота ещё нет.
   Архитектурно это одна точка учёта и одна дисциплина на оба вида
   исполнителей.
2. **Единица учёта — одно обращение через дорожку.** Дорожка записывает
   владельца, вид операции (приоритет, с которым шлюз её занял:
   публикация, действие человека, обслуживание, фон), начало и конец
   тела, исход: успех, ошибка, флуд-лимит (с названным сроком), отмена
   (обрыв загрузки человеком — не ошибка). Отказ до тела (заморозка)
   не записывается: Telegram не тревожили.
3. **Запись на операцию, а не корзины.** Таблица `account_operations`
   (миграция `d7c2e94a1f63`): владелец — ровно одна из двух ссылок
   (`tg_account_id` или `bot_id`, обе CASCADE), вид, начало, конец,
   исход, срок флуд-лимита. Занятость окна считается **при чтении** —
   суммой пересечений интервалов с окном: операция любой длины
   и с любым началом учитывается ровно той частью, что попала в окно.
   Идущая прямо сейчас операция в базе ещё не лежит и добавляется
   из живого состояния дорожки от своего начала до «сейчас».
4. **Сброс пачкой, не по операции.** Дорожки складывают записи в буфер
   шлюза; сервис активности (`engine/services/activity.py`) забирает
   буфер раз в десять секунд и при остановке движка (до остановки шлюза
   и БД), пишет одной транзакцией; записи владельца, которого удалили
   за время операции, пропускаются; сбой записи возвращает пачку
   в буфер. Снимок для интерфейса сбрасывает буфер сам — не отстаёт.
5. **Хранение — год** (`KEEP_DAYS` = 365, решение владельца), уборка
   раз в час; удаление владельца уносит его операции каскадом.
6. **Живое состояние — только в памяти:** чем занята дорожка и с какого
   момента, сколько ждут, остаток заморозки. Меняется каждую секунду,
   писать его в БД бессмысленно.
7. **Показ.** На карточке «Пользователей и ботов» — строка «за 24 ч:
   128 операций · занят 12 % · 1 флуд-лимит» и живая пометка
   («сейчас: публикация · ждут 3», «заморожен ещё 2 мин», «свободен» —
   только у тех, кто может работать: не у приостановленных и не
   вошедших). Снимок читается при показе страницы и раз в пять секунд,
   пока она видна; карточки обновляются на месте, без пересборки.
   Окна снимка — час, сутки, неделя; светофора риска **нет**: пороги
   Telegram не публикует, а выдуманные нормы хуже честных чисел.

## Альтернативы

- **Почасовые корзины в БД.** В 60 раз меньше строк, чем поминутные,
  но операция длиннее часа и границы часов посреди загрузки требуют
  дробления при записи — костыль ради экономии, которой нет. Отклонено.
- **Считать в сервисах.** «Пятое место» правила из ADR-0024: каждый
  новый потребитель Telegram должен был бы помнить об учёте. Отклонено.
- **Считать по журналу.** Разбор лога хрупок и не даёт живого состояния.
  Отклонено.
- **Ключевать бот-операции токеном, без дорожки.** Секрет в ключах
  памяти и вторая точка учёта рядом с дорожкой; боты остались бы
  без заморозки после `RetryAfter`. Отклонено в пользу п. 1.
- **Светофор риска с порогами.** Пороги пришлось бы выдумать;
  отложено до живых наблюдений, показываются числа.

## Последствия

- **Плюсы:** активность обоих видов исполнителей считается в одной
  точке и полна по построению; бот получил заморозку после лимита;
  занятость честна для операций любой длины; данные с первого дня
  копятся под будущую страницу аккаунта (графики по окнам).
- **Минусы / риски:** операции одного бота теперь идут строго по
  очереди (прежде могли пересекаться) — на личных объёмах это
  защита, а не потеря; снимок читает операции за неделю одним запросом
  раз в пять секунд, пока страница видна, — при годовом росте базы
  запрос ограничен индексом по `finished_at`; «занят 12 %» у бота
  малоинформативно (запросы Bot API короткие) — число операций
  для него главное.
- **Что нужно сделать дальше:** при этапе 2 — расписание опроса
  источников поверх дорожек с оглядкой на накопленную занятость.

## Дополнение (2026-09-15, страница аккаунта)

Страница аккаунта построена (`ui/pages/user_page.py`) — одна на оба
вида, пункт живого подменю под «Пользователями и ботами» (главное окно
собирает его по `users_changed`, как подменю сообществ). Без полосы
вкладок: шапка (аватар-буква, имя, плашка состояния, живая пометка,
подстрочник, главное действие по состоянию, меню «…» — пометка,
«Где состоит?», удаление), затем обзор без кнопок — справка, плитки
окон час / сутки / неделя, графики из тех же строк `account_operations`
(операции по часам суток за 7 дней, занятость и флуд-лимиты по дням
за 30 — `ActivityService.history`, чистая `history_stats`: занятость
делится между местными днями пересечением, загрузка через полночь
честно достаётся обоим), виды операций строками с полосой — и список
сообществ только для чтения (`CommunitiesService.communities_of_account`
/ `communities_of_bot`; клик ведёт на страницу сообщества, при ещё
не собранном подменю переход довершается после загрузки дашборда).
Вёрстка карточек общая с «Обзором» сообщества — базовый класс
`OverviewCards` (плитка, карточка графика, строки долей, сетка справки)
и функции `hours_chart` / `days_chart`; действия — общий модуль
`user_actions.py` для дашборда и страницы. Управление членствами
с обратной стороны и журнал операций — отложены до потребности.
