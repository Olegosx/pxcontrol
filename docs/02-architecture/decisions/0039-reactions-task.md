# ADR-0039. Задача «Реакции»: выбранные пользователи ставят реакции записям

> Статус: accepted (реализовано; живая проба — `_misc/tg_reactions_probe.py`, см. «Что нужно сделать дальше»)
> Дата: 2026-09-22 · Автор: olegosx
>
> Первый новый вид задач на основании [ADR-0038](0038-community-tasks.md)
> (задачи, запуски, журнал, расписание); опирается на
> [ADR-0035](0035-community-executors-and-rights.md) (пул исполнителей
> и снимок прав — в нём уже есть разрешение «реакции»),
> [ADR-0036](0036-executor-dispatch-and-urgency.md) (диспетчер даёт
> способных в порядке занятости), [ADR-0024](0024-telegram-account-lane.md)
> (дорожка аккаунта — темп) и [ADR-0026](0026-community-maintenance.md)
> (границы массовой работы, «отказ — пропуск, флуд — конец прохода»).

## Контекст

Требование владельца (21.09.2026): задача «проставление реакций
в сообществе» с параметрами — кто ставит (пользователи пула), какие
реакции (несколько из разрешённых в сообществе, у каждой — вероятность
выпадения), пауза между проходами (случайно в промежутке, например
35–96 минут). Порядок: выбранные пользователи **последовательно** ставят
реакции — под всеми записями без реакции пользователя, под последней
записью или под N случайными без реакции; между пользователями пауза
из промежутка, между реакциями около секунды; под каждую запись —
случайная реакция по весам; аккаунт с Premium может ставить две.
Уточнения 21.09.2026: глубина просмотра — 256 записей, охват
по умолчанию — все без реакции, кнопки «пройти всеми сейчас» не нужно.

### Что об этом говорит Telegram

Сверено 21.09.2026 по core.telegram.org и установленной Telethon 1.44.0;
помеченное «проверить живьём» проверяет проба `_misc/tg_reactions_probe.py`.

- **Разрешённые реакции сообщества** — поле `available_reactions`
  в `channelFull` ([конструктор](https://core.telegram.org/constructor/channelFull)):
  `chatReactionsAll` («любые стандартные», `allow_custom`),
  `chatReactionsSome` (перечень `Reaction`), `chatReactionsNone`
  («запрещены»). Описания стандартных эмодзи и признак «только Premium» —
  в глобальном списке [`messages.getAvailableReactions`](https://core.telegram.org/method/messages.getAvailableReactions)
  (`availableReaction`: `reaction`, `title`, `premium`, `inactive`).
  Что означает **отсутствие** поля — не документировано; *проверить
  живьём*.
- **Постановка** — [`messages.sendReaction`](https://core.telegram.org/method/messages.sendReaction)
  со списком `Reaction` («reactions should be sent in ascending
  order»); список **заменяет** реакции пользователя на записи; флаг
  `add_to_recent` добавляет реакцию в «недавние» клиента. Ошибки:
  `REACTION_INVALID`, `REACTION_EMPTY`, `REACTIONS_TOO_MANY`,
  `PREMIUM_ACCOUNT_REQUIRED`, `MSG_ID_INVALID`, `CHANNEL_PRIVATE`,
  `USER_BANNED_IN_CHANNEL`. Сколько реакций от одного пользователя —
  `reactions_user_max_default` / `reactions_user_max_premium`
  ([конфигурация](https://core.telegram.org/api/config)); у сообщества
  может быть свой потолок разных реакций `reactions_limit`.
- **Своя реакция** — поле `chosen_order` у [`reactionCount`](https://core.telegram.org/constructor/reactionCount):
  «if set, indicates that the current user also sent this reaction».
  У [`messageReactions`](https://core.telegram.org/constructor/messageReactions)
  есть флаг `min` — «constructors that are the same for all users so
  they don't have the reactions sent by the current user»: по такому
  объекту о своей реакции судить нельзя, нужен
  [`messages.getMessagesReactions`](https://core.telegram.org/method/messages.getMessagesReactions).
  Приходит ли история с `min` — *проверить живьём*.
- **Право участника** — `chatBannedRights.send_reactions`
  ([права](https://core.telegram.org/api/rights)); в снимке прав
  исполнителя оно уже есть (`MemberRights.send_reactions`, ADR-0035).
- **Числовых лимитов частоты** реакций документация не задаёт — только
  общий флуд-лимит ([реакции](https://core.telegram.org/api/reactions)).
- В Telethon 1.44.0 высокоуровневой обёртки для реакций нет —
  сырые запросы `SendReactionRequest`, `GetAvailableReactionsRequest`,
  `GetMessagesReactionsRequest` (проверено интроспекцией).

## Решение

1. **Запуск — проход одного пользователя.** Задача хранит в курсоре
   (`community_tasks.cursor`, `{"next": n}`) номер следующего
   по кругу; пауза между проходами — это **интервал расписания**
   задачи (ADR-0038: «случайно в промежутке», умолчание 35–96 мин).
   Довод: очередь не держит слот часами ради сна, перезапуск
   приложения не начинает круг заново, журнал получает строку
   на каждого пользователя — та гранулярность, о которой просили.
   Курсор сдвигается после **завершённого** прохода (в том числе
   «без изменений»): оборванный флуд-лимитом проход повторит тот же
   пользователь следующим сроком.
2. **Кто ставит** — исполнители, названные в параметрах
   (`ReactionsParams.users`, ключи `ExecutorRef`). Способность —
   новое действие `ExecutorAction.REACT` в `abilities.can`:
   администратору всегда, участнику — по `allowed.send_reactions`,
   состоящему в сообществе. Вид выбирает исполнителя сам
   (`choose_executor`, новый пункт контракта `TaskSpec`): следующий
   по кругу из названных, кто **сейчас** способен (не приостановлен,
   состоит, право есть); неспособные пропускаются, и очередь идёт
   дальше. Никто из названных не способен — отказ при постановке
   с объяснением, кого вернуть в строй.
3. **Какие реакции** — набор пар «эмодзи, вес в процентах»
   (`ReactionChoice`); форма предлагает только разрешённые
   в сообществе с описаниями (`userbot_available_reactions`:
   `channelFull.available_reactions` + глобальный каталог, два запроса
   в одном обращении). Веса относительные (50 и 50 = 100 и 100),
   нулевой вес — реакция не выпадает, но остаётся в наборе. Выбор —
   чистая `pick_reaction` (взвешенный случайный); две реакции у Premium
   (`premium_double` и `userbot_premium`) — две **разные** из того же
   розыгрыша. Кастомные эмодзи не предлагаются: только с Premium,
   а стандартных достаточно.
4. **Каким записям** — охват `ReactionScope`: все просмотренные без
   реакции пользователя (умолчание), последняя запись, N случайных без
   реакции. Записи со своей реакцией не берутся ни в одном охвате:
   `sendReaction` **заменяет** реакции пользователя, вторая стёрла бы
   первую. Отбор — чистая `select_targets` с потолком за проход.
5. **Границы обязательны** (ADR-0026): глубина просмотра (умолчание
   256 — три запроса), потолок реакций за проход (умолчание равен
   глубине: второго числа владелец не просил, а потолок у массовой
   работы обязателен), пауза между реакциями случайно в промежутке
   (умолчание 0,7–1,5 с; ноль — только зазор дорожки; прерывается
   остановкой движка через `TaskContext.sleep`).
6. **Перед проходом — сверка с сообществом.** Режим «запрещены» —
   запуск с ошибкой «задача невыполнима»; при режиме «некоторые»
   эмодзи не из перечня выбрасываются из набора с записью в журнал;
   пустое пересечение — ошибка. Отказ по одной записи
   (`UserbotReactionError`: `REACTION_INVALID`, `REACTIONS_TOO_MANY`,
   `PREMIUM_ACCOUNT_REQUIRED`; исчезнувшая запись) — пропуск, а не конец
   прохода; флуд-лимит — конец прохода (ADR-0017).
7. **Граница шлюза** (`telegram/types.py`): `ChatReactions` (режим,
   `ReactionOption`), `ReactablePost` (номер, дата, свои реакции),
   `ReactionsPage`. Транспорт: `available_reactions`, `reactions_page`
   (страница ленты без служебных записей; при флаге `min` дочитывает
   реакции текущего аккаунта по номерам страницы — второй запрос в том
   же обращении), `send_reaction` (список `ReactionEmoji`,
   `add_to_recent=False` — задача не должна менять панель быстрых
   реакций человека в его клиенте). Шлюз — обёртки с приоритетом
   `MAINTENANCE`; для формы тот же перечень тем же приоритетом
   (одно короткое обращение, второго приоритета у операции не бывает —
   правило `userbot_delete_messages`).
8. **Запуск «без изменений»** — подбор записей: лента читается,
   подходящие считаются, реакции не ставятся. Курсор при этом тоже
   сдвигается: проход состоялся, пусть и пустой.
9. **Интерфейс** — раздел «Реакции» во вкладке «Задачи»: два списка
   галочками (пользователи с правом реагировать, включая
   приостановленных с пометкой; реакции сообщества с весом), охват
   и число случайных, глубина и потолок, паузы, флажок Premium,
   «Подобрать записи» и «Провести проход», расписание и журнал как
   у других видов. Включение расписания подтверждается один раз
   (число пользователей, охват, потолок).
10. **Риск назван, а не спрятан.** Массовые реакции с пользовательских
    аккаунтов — та же автоматизация, за которую Telegram ограничивает
    аккаунты (ADR-0011 принял риск для публикации, ADR-0026 — для
    уборки). Сдерживают его паузы, потолок за проход, интервал между
    проходами, круг по пользователям и остановка при флуд-лимите;
    предельный темп узнаётся наблюдением, а не штурмом.

## Альтернативы

- **Запуск = все пользователи подряд с паузами внутри.** Ближе
  к дословной формулировке требования, но задание висело бы в очереди
  часами ради сна, перезапуск начинал бы круг заново, а журнал
  получал бы одну строку на круг вместо строки на пользователя.
  Отклонено (согласовано с владельцем 21.09.2026).
- **Реакция через бота.** Bot API ставить реакции умеет
  (`setMessageReaction`), но бот — один и виден как бот; требование —
  реакции от пользователей пула. Отклонено.
- **Второй запрос на каждую запись для проверки своей реакции.**
  Точнее, но удваивает число запросов; `chosen_order` в истории даёт
  ответ бесплатно, а дочитывание по `min` — один запрос на страницу.
  Отклонено.
- **Хранить перечень реакций сообщества в базе.** Экономит одно
  обращение при открытии формы, но перечень меняет администратор
  в Telegram, и устаревшая копия обещала бы эмодзи, которые сервер
  отвергнет. Отклонено: читается при показе формы и перед проходом.
- **Курсор сдвигать и при оборванном проходе.** Проще, но флуд-лимит
  на одном пользователе «съедал» бы его очередь; повтор тем же
  пользователем честнее. Отклонено.

## Последствия

- **Плюсы:** задача ложится на контракт ADR-0038 без правок очереди
  и журнала (добавлены только курсор, пауза и выбор исполнителя видом);
  выбор реакции, отбор записей и круг — чистые функции с тестами;
  сырые объекты Telethon выше границы не поднимаются.
- **Минусы / риски:** три утверждения о Telegram не подтверждены
  документацией словами (отсутствие поля `available_reactions`,
  `min` в истории, две реакции с Premium) — до живой пробы поведение
  на них считается предположением; форма делает два чтения
  (пользователи и перечень) при каждом показе; риск ограничения
  аккаунта (п. 10).
- **Что нужно сделать дальше:** прогнать `_misc/tg_reactions_probe.py`
  на тестовых сообществах (шаги `options`, `mine`, `premium`, `pass`)
  и записать итог дополнением; по итогу — при необходимости поправить
  чтение своих реакций и трактовку отсутствующего поля.
