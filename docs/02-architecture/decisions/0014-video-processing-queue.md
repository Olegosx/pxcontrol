# ADR-0014. Пакетная обработка видео через единую очередь в памяти движка

> Статус: accepted
> Дата: 2026-08-15 · Автор: olegosx
>
> Опирается на [ADR-0012](0012-publish-queue-in-memory.md) (очередь
> отправки постов) и уточняет страницу «Видео» из [ADR-0006](0006-desktop-pyside6.md).
>
> ⚠️ Дополнение (2026-08-24): параметры обработки — **у каждой заявки
> свои** (`ProcessingRequest` несёт `fields` и подпапку пакета), а не
> общие на пакет. Источник на странице «Видео» — список карточек
> файлов с индивидуальными панелями параметров; карточка-шаблон
> «[Параметры пресета]» задаёт параметры добавляемых файлов и служит
> пресетам. Панель параметров в каждой карточке — тяжёлый набор
> виджетов: модель рассчитана на десятки файлов в списке, не сотни.

## Контекст

Обработка видео была строго одиночной: «Обработать» запускал один ffmpeg
и блокировал кнопку до конца кодирования. Для наполнения каналов нужна
пакетная обработка: выбрать папку, рекурсивно найти в ней видео
и прогнать выбранные через одни и те же параметры. Прямолинейное
«запустить N обработок» не годится: кодировщик x264 сам загружает все
ядра процессора — параллельные ffmpeg не ускоряют пакет, а дерутся
за процессор; кроме того, нужен видимый ход пакета, отмена и повтор
неудачных файлов.

## Решение

1. **Единая очередь обработки** — `ProcessingQueue`
   (`engine/services/video_queue.py`), по образцу очереди отправки
   (ADR-0012): в памяти цикла событий движка, строго последовательная,
   карточки со статусом/прогрессом/отменой/повтором, интерфейс опрашивает
   состояние таймером. **И одиночная, и пакетная обработка идут через
   неё** — одиночный файл равен пакету из одного элемента, логика
   выполнения не двоится.
2. **Персистентности нет** — очередь не переживает перезапуск
   (подтверждение при закрытии окна, общее с очередью отправки).
   Риск мал: результат пишется атомарно (`.part` → `os.replace`),
   готовые файлы уже на диске, остальное ставится заново.
3. **Сканирование папки** — `VideoService.scan_sources`: рекурсивный
   обход в отдельном потоке с длительностью каждого файла через ffprobe
   (ход виден в диалоге). Папки результатов и опубликованных исключаются;
   скрытые файлы/папки и недописанные `.part` пропускаются. Пользователь
   отмечает галочками, что обрабатывать (нечитаемые ffprobe файлы
   по умолчанию сняты).
4. **Подпапка пакета**: результаты пакета кладутся
   в `<результаты>/<подпапка пресета>/<штамп>_<имя папки-источника>/` —
   пакет отделён от одиночных результатов и других пакетов. Список
   «Готовые видео» из-за этого обходит подпапку пресета **рекурсивно**
   (имя показывается с подпапкой), а перенос в «опубликованные» вложение
   сохраняет («зеркалим относительный путь», без изменений).
5. **Интерактивный источник кадра заставки** («случайные кадры
   на выбор») несовместим с фоновой очередью, поэтому кадры выбираются
   **до постановки**: диалог выбора по разу на файл; выбранный PNG
   копируется в папку очереди (`stash_frame`) — следующая партия
   кандидатов стёрла бы его. Отмена выбора для пакета — предложение
   исключить файл, остальные не теряются.
6. **Авто-битрейт**: исходник больше лимита Telegram (2000/4000 МиБ)
   получает рекомендуемый битрейт «лимит минус 1 %» автоматически
   (спросить пользователя посреди пакета нельзя); заданный вручную
   битрейт ниже рекомендации не повышается. Пометка — в карточке
   элемента.
7. **Отмена работающего кодирования** — кооперативная: колбэк прогресса
   бросает служебное исключение, `run_streaming` убивает процесс ffmpeg
   (механизм уже был закреплён тестом). Фазы без прогресса (ffprobe,
   кадр заставки, вшивание обложки) не прерываются — отмена подхватится
   на первой строке прогресса; остановка движка ждёт воркер с таймаутом.

## Альтернативы

- **Очередь в БД (переживает перезапуск).** Плюс — пакет продолжается
  после рестарта; минусы — таблица, миграция, восстановление «висящих»
  элементов и расхождение с принципом «истина — файлы на диске».
  Атомарная запись результата решает главный риск дешевле. Отклонено.
- **Параллельная обработка (пул ffmpeg).** Не даёт выигрыша: x264
  утилизирует все ядра одним процессом, а прогресс и отмена усложняются
  кратно. Отклонено.
- **Общий базовый класс с `PublishQueue`.** Семантика различается
  (отмена сетевой загрузки против убийства процесса, разные проверки
  при постановке); пока очередей две, дублирование каркаса дешевле
  преждевременной абстракции (YAGNI). Пересмотреть при третьей очереди.
- **Оставить одиночную обработку отдельным путём.** Два кода запуска
  ffmpeg и конкуренция за процессор при одновременном запуске. Отклонено.

## Последствия

- **Плюсы:** пакетная обработка папки «поставил и ушёл»; один код
  выполнения на оба сценария; ошибки файлов изолированы и повторяемы;
  форма страницы «Видео» свободна во время кодирования.
- **Минусы / риски:** очередь пропадает при перезапуске (осознанно,
  как ADR-0012); выбор кадров для большого пакета — ручной
  последовательный проход; отмена в фазах без прогресса срабатывает
  с задержкой.
- **Что дальше:** будущая автоматика (источники, этап 2) сможет ставить
  элементы в ту же очередь без интерфейса.
