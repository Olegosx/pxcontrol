# ADR-0044. Битрейт при смене разрешения: постоянное качество или пересчёт по площади

> Статус: accepted
> Дата: 2026-09-26 · Автор: olegosx
>
> Уточняет правило «Качество — как в оригинале» модуля
> [«Подготовка видео»](../../03-modules/video-processing.md); не трогает
> авто-битрейт под лимит Telegram из
> [ADR-0014](0014-video-processing-queue.md) (п. 6).

## Контекст

Битрейт видео в пресете по умолчанию не задан («0 — как в оригинале»),
и конвейер брал битрейт исходника из ffprobe. Разрешение при этом
по умолчанию — ступень 1080. Значит, ролик 4K (3840×2160, площадь кадра
в 4 раза больше FullHD) уменьшался до 1920×1080, но кодировался битрейтом
4K: x264 в режиме среднего битрейта (`-b:v`) тратит отведённый бюджет,
и итог выходил в разы тяжелее нужного. Обратный случай — увеличение
720 → 1080 — получал битрейт 720p и замыливался.

Размер кадра на выбор качества не влиял вовсе: функция выбора
(`_video_quality_args`) знала только битрейт пресета и исходника.

## Решение

Новое поле пресета `rescale_bitrate_mode` — **режим битрейта при смене
разрешения** (перечисление `RescaleBitrateMode` в
`engine/video/constants.py`). Порядок выбора качества:

1. Явный битрейт пресета — главнее всего (как и раньше; так же и
   авто-битрейт под лимит Telegram, он задаётся явно).
2. ffprobe не сообщил битрейт исходника — постоянное качество CRF 20
   (как и раньше).
3. Размер кадра не меняется — битрейт исходника (как и раньше).
4. Размер кадра меняется — по режиму:
   - **`crf` — постоянное качество, по умолчанию.** `-crf 20`
     (Constant Rate Factor: кодек сам подбирает битрейт под уровень
     качества; шкала 0–51, меньше — лучше, умолчание x264 — 23).
     Кодек тратит столько бит, сколько нужно картинке нового размера,
     без эмпирических коэффициентов.
   - **`scale` — пересчёт от исходника.** `-b:v` со значением
     `битрейт исходника × (площадь итога / площадь исходника) ^ 0,71 × 1,10`.

Показатель степени 0,71 и запас 1,10 — константы
`RESCALE_BITRATE_EXPONENT` и `RESCALE_BITRATE_MARGIN`.

**Показатель степени.** Эмпирическое «правило степени 0,75» Бена
Ваггонера (специалист по сжатию видео, Microsoft, затем Amazon): битрейт
для того же качества растёт не пропорционально числу пикселей, а как
его степень меньше единицы — на крупном кадре каждый дефект сжатия
мельче, и бит на пиксель нужно меньше. Показатель зависит от кодека:
0,75 выводили для WMV и VP6, для VC-1 (поколение H.264) Microsoft
использовала 0,71; чем эффективнее кодек, тем ниже показатель.
Отдельного замера для H.264 нет, берём 0,71: это документированное
значение для кодека того же поколения, а при уменьшении кадра меньший
показатель оставляет больше битрейта — безопасная сторона.

**Запас 10 %.** Правило — оценка, а цель режима — итог не хуже
исходника. Запас ложится поверх нелинейного пересчёта.

Ориентиры (доля битрейта исходника, с запасом):

| Переход | Линейно | ^0,71 × 1,10 |
|---|---|---|
| 4K → 1080 | 0,28 | 0,41 |
| 1440 → 1080 | 0,62 | 0,73 |
| 1080 → 720 | 0,49 | 0,62 |
| 720 → 1080 (апскейл) | 2,48 | 1,96 |

Существующие пресеты миграцией `b8d4e27a6c15` получают `crf`: прежнее
поведение (битрейт исходника без пересчёта) сознательно не сохраняется —
его исправление и есть цель решения.

В форме — список «Битрейт при смене разрешения» в карточке «Вывод»;
активен, только когда режим может подействовать (битрейт — 0,
выбрана ступень разрешения).

## Альтернативы

- **Оставить битрейт исходника.** Плюс — размер итога предсказуем.
  Минус — расточительность при уменьшении кадра в 2,5–3,5 раза
  и замыливание при увеличении. Отклонено: это и есть проблема.
- **Только постоянное качество, без выбора.** Проще, но размер итога
  заранее неизвестен; для тех, кому важна предсказуемость размера,
  нужен режим с пересчётом. Оставлено режимом по умолчанию.
- **Только пересчёт по площади.** Опирается на эмпирический
  коэффициент, который для H.264 не измерен. Оставлено вторым режимом.
- **Потолок битрейта для CRF (`-maxrate` + `-bufsize`).** Механизм
  VBV (буфер контроля битрейта) x264 ограничил бы выбросы на сложных
  сценах. Не вводим: лишние параметры без запроса; можно добавить,
  если выбросы проявятся (YAGNI).

## Последствия

- **Плюсы:** уменьшение кадра больше не тащит битрейт исходника —
  итог 4K → 1080 легче в разы; апскейл в режиме пересчёта получает
  битрейт по новой площади. Выбор качества — одна чистая функция,
  проверяемая без ffmpeg.
- **Минусы / риски:** в режиме `crf` размер итога заранее неизвестен.
  Рекомендация битрейта под лимит Telegram по-прежнему смотрит только
  на размер исходника: итог, выросший при апскейле в режиме `scale`,
  может выйти за лимит, хотя исходник в него укладывался. При уменьшении
  кадра — основном сценарии — итог меньше исходника в обоих режимах.
  Показатель 0,71 — оценка, а не замер на H.264.
- **Что нужно сделать дальше:** при необходимости — замер показателя
  на реальных роликах канала (например, по VMAF — метрике качества
  видео от Netflix) и уточнение константы.

## Источники

- Встроенная справка ffmpeg 8.0.1: `ffmpeg -h encoder=libx264`
  (`-crf`), `ffmpeg -h full` (`-b`, `-maxrate`, `-bufsize`).
- [FFmpeg Codecs Documentation — libx264](https://ffmpeg.org/ffmpeg-codecs.html#libx264_002c-libx264rgb);
  справка x264 (`x264.c`) и умолчания (`common/base.c`: CRF 23)
  в [репозитории x264](https://code.videolan.org/videolan/x264).
- Правило степени: [Streaming Learning Center — Estimating the Bitrate for 8K Videos](https://streaminglearningcenter.com/ffmpeg/estimating-the-bitrate-for-8k-videos.html),
  [Jan Ozer — Five Views of Your Encoding Ladder](https://www.linkedin.com/pulse/five-views-your-encoding-ladder-jan-ozer)
  (показатели 0,75 и 0,71).
