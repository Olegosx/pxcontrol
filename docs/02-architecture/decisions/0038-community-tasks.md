# ADR-0038. Задачи сообщества: виды, запуск по требованию и по расписанию, журнал запусков

> Статус: accepted (этап A выполнен; B–E — см. «Что нужно сделать дальше»)
> Дата: 2026-09-22 · Автор: olegosx

> (дорожка аккаунта), [ADR-0035](0035-community-executors-and-rights.md)

## Контекст

Обслуживание сообщества (ADR-0026) — два вида уборки на общем каркасе
заданий: чистка служебных записей и удаление мёртвых аккаунтов. Оно
запускается только человеком, ничего о себе не помнит между запусками
(ни параметров, ни итогов — только строки в общем журнале приложения)
и не умеет работать по расписанию: ADR-0026 п. 10 прямо отложил это
до «общего планировщика», а ADR-0017 запретил заводить частные таймеры.

Требования владельца (21.09.2026):

- вкладка «Обслуживание» переименовывается в **«Задачи»**, и это слово
  становится термином для сущностей вкладки;
- работа с задачами должна быть **системной**: запуск по требованию
  и по расписанию, отчёт о выполнении — свой мини-журнал по каждой
  задаче в каждом сообществе;
- следом на этом основании появляются новые виды: проставление
  реакций и приём заявок на вступление.

Что уже есть и что определяет решение (сверено по коду 21.09.2026):

1. **Каркас заданий** (`JobQueue`, ADR-0025 с дополнением ADR-0036)
   умеет слоты, замки заданий, удержания и крючок «запиши исход до
   смены статуса в памяти». Ничего из этого менять не нужно.
2. **Периодической работы** в движке три вида — опрос статистики,
   дозор кнопок, сброс активности, — и все живут на общем тикере
   `PeriodicTask`. Общего планировщика *пользовательских* задач нет.
3. **Снимок прав исполнителя** (ADR-0035) уже несёт разрешение
   участника «реакции», и ADR-0035 заводился с оговоркой «следующие
   задачи ухода не требуют админских прав» — фундамент под новые виды
   готов.
4. **Исполнителя под операцию** выбирает диспетчер (ADR-0036) в момент
   попытки, а не при постановке.

## Решение

1. **Три термина.** **Задача** — сохранённая настройка сообщества:
   вид, параметры, расписание, включена ли. **Запуск** — одно
   выполнение задачи: кто запустил, чьими руками, когда, чем кончилось,
   отчёт и события. **Задание** — элемент очереди каркаса, который
   несёт запуск, пока тот выполняется (термин ADR-0025, не меняется).
   Задача живёт в базе, задание — в памяти, запуск — строка журнала.
2. **Хранение** (миграция `e3f9a2c7d514`): `community_tasks` — строка
   на пару «сообщество + вид», ровно одна (`uq_community_task_kind`),
   заводится при первом обращении к виду с умолчаниями вида; поля —
   `params` (JSON вида), `schedule` (JSON расписания), `cursor`
   (состояние вида между запусками), `enabled`, `next_run_at`,
   `last_run_at`. `task_runs` — журнал: `trigger` (вручную · по
   расписанию), `dry_run`, исполнитель видом и id (как у операций,
   ADR-0030), `started_at` / `finished_at`, `outcome`, `report` (JSON
   отчёта вида), `events` (события списком, не больше 500 на запуск),
   `error`. Обе таблицы — каскадом с сообществом. Прецедент хранения
   структур JSON — снимок прав и разобранная статистика.
3. **Строка запуска заводится в начале работы** со значением «идёт»
   и дописывается крючком `record` каркаса до смены статуса в памяти
   (ADR-0025, п. 7). Падение приложения оставляет честное «начат,
   не завершён». Отмена человеком и остановка движка — разные исходы
   (`cancelled` / `interrupted`): первая — решение, вторая —
   обстоятельство. Неполный отчёт при обрыве не строится (ADR-0026,
   п. 7), но события остаются — след для разбора.
4. **Вид задачи — спецификация одного контракта** (`TaskSpec`
   в `engine/tasks/model.py`): параметры с проверкой границ и переводом
   в JSON, нужное исполнителю право (`ExecutorAction`) для такого
   запуска, выполнение шагами с проверкой остановки между шагами,
   отчёт с переводом в JSON и итогом одной строкой. Виды живут
   в пакете `engine/tasks/` (по образцу `engine/video/` — предметные
   модули без интерфейса); реестр `SPECS` — единственное место, где
   перечислены виды. Сервис задач (`engine/services/tasks.py`) знает
   только контракт: постановка, очередь, журнал, расписание и вкладка
   общие для всех видов. Два вида ADR-0026 переехали в пакет без
   изменения поведения.
5. **«Без изменений» — свойство запуска, а не параметр задачи.**
   Просмотр служебных записей и поиск мёртвых аккаунтов — тот же вид
   с признаком `dry_run`; он записывается в журнал. Правило ADR-0026
   п. 3 для ручного запуска сохраняется: сначала «Просмотреть», потом
   удаление с подтверждением. Для запуска по расписанию подтверждение
   даётся **один раз при сохранении расписания** (этап B): диалог
   перечислит выбранные виды и предел за проход. Это уточнение
   ADR-0026, п. 3, записано там дополнением.
6. **Очередь — с несколькими слотами, замок — сообщество.**
   `JobQueue(concurrency=PARALLEL_TASKS)` (3, по прецеденту потолка
   загрузок ADR-0036; подлежит проверке живьём, в настройки
   не выносится — ADR-0013). Задачи разных сообществ идут одновременно,
   в одном сообществе — не больше одной (замок задания, ADR-0036):
   отчёты не пересекаются, лента не получает два потока действий разом.
   Темп внутри аккаунта держит дорожка (ADR-0024), приоритет —
   `MAINTENANCE` для всех видов: те же сотни однотипных запросов
   подряд, что у уборки. Вид работы в учёте активности — «обслуживание».
7. **Исполнитель выбирается в момент запуска**, а не при постановке —
   как у очереди отправки после ADR-0036: `executors_for(community,
   action)` по свежему снимку прав и живой занятости дорожек. При
   постановке лишь проверяется, что способный в пуле есть: отказ
   «некому» должен звучать при нажатии кнопки, а не через час
   в журнале. Уточняющий зонд прав для строк без снимка (ADR-0035,
   этап E) сохранён. Задачи по-прежнему ведут только пользователи
   (ADR-0026, п. 8).
8. **Расписание** (этап B) — значение с тремя видами: «только по
   требованию», «интервал» (каждые N минут либо случайно в промежутке
   [min, max]) и «в моменты суток» (список «ЧЧ:ММ», формат
   `publish_times`). Следующий момент считает чистая функция и
   **сохраняет** в `next_run_at`: случайный интервал вытягивается один
   раз после окончания запуска, человек видит «следующий запуск
   в 14:37», перезапуск приложения ничего не сдвигает. Планировщик —
   один `PeriodicTask` с тиком в минуту (как у статистики): берёт
   задачи с наступившим сроком и ставит задание, если такой задачи
   в очереди ещё нет; пропущенные за время выключения запуски
   догоняются один раз; выключенное сообщество (`enabled`)
   пропускается; журнал старше 90 дней убирается раз в сутки.
   Останавливается первым из компонентов, до очередей.
9. **Интерфейс.** Вкладка `TAB_TASKS` «Задачи» (ключ `tasks`), окно
   с дашборда «Задачи · Название», кнопка карточки и пункт меню —
   «Задачи». Тело — разделы-сегменты по одному на вид (форма
   параметров, запуск, итог, «Журнал…»), внизу общая панель хода
   работы; журнал — рабочее окно с таблицей запусков и событиями
   выбранного. Разделы по видам, а не список задач с «Добавить»:
   у сообщества ровно одна задача каждого вида, добавлять нечего.
10. **Вне объёма этого решения:** сами новые виды — реакции
    ([ADR-0039](0039-reactions-task.md)) и приём заявок
    ([ADR-0040](0040-join-requests-task.md)); перевод внутренних
    дозоров движка (статистика, кнопки, активность) на планировщик
    задач — они не настраиваются человеком, и переезд не даёт ничего,
    кроме риска; источники контента этапа 2 ложатся в «задачи»
    естественно (парсинг источника — вид задачи с расписанием),
    но это отдельное решение.

## Альтернативы

- **Оставить `MaintenanceService` и добавить таймер.** Дёшево, но это
  ровно то, что запретили ADR-0017 и ADR-0026 п. 10; на третьем виде
  появилась бы третья копия «запуск + отчёт». Отклонено.
- **Задачи только в памяти, без базы.** Не переживают перезапуск,
  журнала нет — противоречит требованию об отчёте. Отклонено.
- **Сторонняя библиотека планирования.** Нечего планировать сложнее
  «момент следующего запуска в базе плюс тик раз в минуту»;
  `PeriodicTask` уже есть. Отклонено.
- **Одна очередь на всё, как у обслуживания (один слот).** Одна долгая
  задача в одном сообществе держала бы все остальные; замок сообщества
  даёт тот же порядок внутри сообщества без этой цены. Отклонено.
- **Исполнитель фиксируется при постановке** (как было у обслуживания).
  Запуск по расписанию может случиться через часы, когда исполнитель
  занят загрузкой или приостановлен; свежий подбор в момент запуска —
  правило ADR-0036 для всех операций сообщества. Отклонено.
- **Список задач с кнопкой «Добавить задачу»** вместо разделов по видам.
  Гибче, если задач одного вида несколько; но их ровно одна на вид
  (п. 2), и лишний шаг «добавить» не даёт ничего. Отклонено; снять
  уникальность и перейти к списку проще, чем разбираться с дублями
  сейчас.
- **Хранить итог только в общем журнале приложения** (как было). Строки
  в файле не привязаны ни к задаче, ни к сообществу, и человек не видит
  их с экрана. Отклонено.

## Последствия

- **Плюсы:** запуск оставляет след, который видно с экрана: кто,
  когда, чьими руками, чем кончилось; параметры переживают перезапуск;
  новый вид задачи — модуль по контракту и форма, без правок очереди
  и журнала; задачи разных сообществ не ждут друг друга; расписание
  ложится на ту же модель без второго механизма.
- **Минусы / риски:** две новые таблицы и миграция; строка запуска
  пишется трижды за запуск (начало, исполнитель, исход) — на личных
  объёмах это единицы записей в минуту; число слотов и приоритет —
  предположения до живой проверки; вкладка стала шире (журнал,
  расписание), и её тесты — тоже.
- **Что нужно сделать дальше** (этапами, каждый отдельным коммитом
  с тестами и документами):
  1. **этап A** ✅ — модель и хранилище, пакет видов с двумя
     нынешними, сервис задач, журнал запусков, вкладка «Задачи»
     с прежними формами и окном журнала; поведение уборки
     не меняется (тесты перенесены без правок по смыслу);
  2. **этап B** — расписание: значение, `next_run`, планировщик, форма
     расписания в разделах, подтверждение чистки при сохранении,
     уборка журнала;
  3. **этап C** — реакции (ADR-0039): типы и транспорт, вид задачи,
     форма, проба живьём;
  4. **этап D** — приём заявок (ADR-0040): типы и транспорт, вид
     задачи, форма, проба живьём;
  5. **этап E** — порог `flood_sleep_threshold = 0` у клиента Telethon:
     библиотека по умолчанию сама молча спит при флуд-лимите короче
     60 с, и дорожка (ADR-0024) с учётом активности (ADR-0030) о нём
     не узнают; массовые задачи ловят такие лимиты чаще всех.
