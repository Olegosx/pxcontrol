# Ожидание публикации: очередь отправки и отложенные записи

> Статус: 🟢 реализовано · Обновлено: 2026-09-21 · Владелец: olegosx
>
> Решения — [ADR-0010](../02-architecture/decisions/0010-posts-fire-and-forget.md)
> (отложенные хранит сервер Telegram), [ADR-0016](../02-architecture/decisions/0016-persistent-publish-queue.md)
> (очередь отправки), [ADR-0028](../02-architecture/decisions/0028-scheduled-posts-as-queue.md)
> (отложенные как очередь: правка на сервере, общий список карточек),
> [ADR-0032](../02-architecture/decisions/0032-publishing-section-post-stages.md)
> (стадии поста — экраны раздела «Публикация»).

## Назначение

Две стадии ожидания отвечают на вопрос «что будет опубликовано
и когда»: пост либо ждёт отправки **у нас** (экран «Очередь»), либо уже
принят **сервером Telegram** (экран «Отложено»). Оба экрана — пункты
раздела «Публикация», третий и четвёртый шаги пути поста (ADR-0032);
до 17.09.2026 они были вкладками отдельной страницы «Расписание»,
которой больше нет. **Своего планировщика в приложении нет**: отложенную
запись создаёт публикация (`schedule_date` через userbot), а хранит
и публикует её **сервер Telegram** — приложение и компьютер могут быть
выключены.

## Два списка — два экрана

| | **Отложено** | **Очередь** |
|---|---|---|
| Где живёт пост | на сервере Telegram | в приложении (таблица `publish_queue_items`) |
| Уйдёт ли при выключенном приложении | да — публикует сервер | нет — ждёт слота или отправки в приложении |
| Откуда список | обход включённых сообществ (`getScheduledHistory`) | состояние очереди движка |
| Обновление | при показе (не чаще раза в минуту), кнопкой «Обновить», после действия — одно сообщество | по уведомлению движка (ADR-0034); прогресс — опросом, пока идёт отправка |
| Статус, прогресс | нет | есть (каркас заданий, ADR-0025) |
| Действия у карточки | «Сейчас», «Удалить», правка текста и времени | «Отмена», «Повторить», «Убрать», правка поста |
| Сортировка | ближайшие / по сообществам | + порядок постановки |
| Фильтры | сообщество, слот времени | + статус |

Разница неочевидна и важна, поэтому каждый экран говорит о ней строкой
под своим заголовком (`stage_hint`). Всё остальное у списков одно: карточка
с логотипом сообщества и цветной меткой слота в шапке, подпись
«сообщество · публикация: когда · …», раскрытие кликом в форму
правки, страницы по 50, итоговая строка и перелистывание.

## Экран «Отложено»

- **Чтение.** Опрашиваются только включённые сообщества с userbot
  (у бот-сообщества отложенных быть не может — Bot API их не умеет).
  Канал — аккаунтом-умолчанием (отложки канала общие для админов),
  группа — **всеми участниками** (ADR-0022): отложку в группе видит
  только её создатель, подтверждено живым прогоном 2026-09-06.
  Ошибка одного опроса не роняет список — сообщество пропускается,
  подробности уходят в лог.
- **Неполный список честно назван неполным.** Движок возвращает
  записи и названия сообществ, которые прочитать не удалось
  (`ScheduledList.unread`), и страница пишет об этом над списком.
  Иначе пустой список читался бы как «отложенных нет», хотя часть
  сообществ просто не спросили, — а истина живёт на сервере.
- **Обход не дублируется и не повторяется зря.** Свежий список
  (моложе минуты) при показе не перечитывается; пока обход идёт,
  второй не начинается. Праздное переключение экранов ставило бы обходы
  один поверх другого, а флуд-лимит, пойманный на обходе, замораживает
  дорожку аккаунта целиком (ADR-0024) — ждать его будет уже публикация.
  Кнопка «Обновить» перечитывает всегда: это явная воля человека.
- **Адрес записи — тройка** `ScheduledRef`: сообщество, аккаунт, чьим
  чтением запись попала в список (в группе править может только
  создатель), id записи в очереди отложенных (он уникален внутри
  сообщества и не совпадает с id в ленте после публикации). Дубли
  от нескольких читателей схлопываются по id, а не по «текст + время»:
  два одинаковых поста — два поста.
- **Правка.** Клик по карточке раскрывает форму; запись читается
  **с сервера целиком** (`PostsService.scheduled_draft`) — её могли
  поправить из другого клиента, снимку списка верить нельзя. Правятся
  текст (у записи с вложением — подпись; предел длины по Premium
  аккаунта-читателя, счётчик под полем) и момент публикации
  (не ближе минуты). Вложение и тема форума показаны сноской
  и не правятся: у `messages.editMessage` нет адресата темы, а замена
  файла — загрузка с прогрессом, то есть задание очереди, а не правка;
  такую запись удаляют и создают заново на «Новом посте». Переключатель
  «сейчас» в форме выключен с подсказкой: для этого у карточки кнопка.
- **«Сейчас» и «Удалить»** — с подтверждением, оба необратимы:
  первое отправляет запись в ленту немедленно
  (`messages.sendScheduledMessages`), второе снимает её, не публикуя
  (`messages.deleteScheduledMessages` — обычное удаление сообщений
  для очереди отложенных не годится).
- **После действия перечитывается только затронутое сообщество**
  (`list_scheduled(community_id)`), а не весь обход, — и после
  удачного, и после отказа: записи могло уже не быть (опубликована
  или удалена с телефона), и тогда карточка должна исчезнуть, а не
  остаться с кнопками в никуда. Исчезнувшая запись — `ScheduledGoneError`,
  штатная гонка с сервером-истиной. Правило одно на все действия: правка
  перечитывает сообщество и при отказе (17.09.2026) — он мог прийти
  именно потому, что записи на сервере больше нет; текст ошибки при этом
  остаётся в форме, набранное не теряется.
- **Неудачное перечитывание не стирает записи** (17.09.2026). Если
  чтение одного сообщества не удалось, его записи остаются прежними,
  а само оно попадает в строку о непрочитанном: пустой ответ означает
  «не спросили», а не «отложенных нет», и подменять им список нельзя.
  Сообщества в этой строке различаются по идентификатору, а не по
  названию, — названия не уникальны.
- **Отложенный опрос** читается как `MediaKind.POLL`, и заголовком
  карточки служит его вопрос: своего текста у опроса нет. Правится
  у него только время — ни вопрос, ни варианты Telegram менять не даёт
  (ADR-0033, C5).
- **Вложения не наших видов** (геопозиция, контакт — поставлены
  отложенными из клиента Telegram) читаются как `MediaKind.OTHER`:
  карточка их показывает, правится только время.
- Переход с дашборда («Отложено» на карточке сообщества) открывает
  экран с фильтром по этому сообществу — без нового обхода, если
  список свежий.

## Экран «Очередь»

Полный живой список очереди отправки: сортировка (ближайшие / порядок
постановки / по сообществам; отправляющийся пост стоит первым при
любой — это единственная карточка с полосой прогресса, а по дате
в очереди из сотен он оказывался где угодно), фильтры по статусу,
сообществу и слоту,
страницы по 50, правка поста в раскрытой карточке
([ADR-0016](../02-architecture/decisions/0016-persistent-publish-queue.md),
п. 6–7). Опрос движка идёт только пока экран виден. Сюда ведут кнопки
«Вся очередь…» на «Новом посте» (там — ближайшие 20 карточек и сводка)
и на странице сообщества (фильтр по нему), действие «Очередь» карточки
дашборда (фильтр по сообществу) и плашка «N ошибок» сводки дашборда
(фильтр «ошибки»).

**Владение очередью отделено от показа** (ADR-0032, ADR-0034).
**Наблюдатель очереди** (`ui/queue_watcher.py`) — один на очередь,
живёт при главном окне (реестр `QueueWatchers`) и не зависит от того,
какой экран открыт: он подписан на движок и получает уведомление
о каждом изменении состава и состояний (в покое обращений к движку
нет), держит последний снимок, снимает завершённые задания и читает
прогресс опросом раз в полсекунды — только пока идёт отправка; он же
отвечает на вопрос при закрытии окна, идёт ли отправка прямо сейчас.
Все остальные — **зрители** (`QueueView`): плашку об исходе
(«Опубликовано», «Отложенная запись создана», «Отправка отменена»)
показывает постоянный зритель окна, панели экранов присоединяются
на время показа и рисуют карточки из кэша наблюдателя (листание
и смена фильтра в движок не ходят). Раньше у каждой панели был свой
наблюдатель с опросом по таймеру, три из них работали с запуска
и никогда не гасились (аудит 19.09.2026), а владельцем очереди
отправки была панель страницы «Публикация» — только потому,
что страница всегда существовала.

Сама очередь — [ADR-0016](../02-architecture/decisions/0016-persistent-publish-queue.md):
«Отправить» ставит пост в хвост и сразу освобождает форму; посты уходят
последовательно, очередь переживает перезапуск. Telegram ограничивает
отложки **100 на канал** (Premium лимит не увеличивает; горизонт — год):
посты сверх лимита ждут в очереди со статусом «ждёт слота» и уходят
по мере освобождения слотов (проверка раз в N минут, настройка) —
**только при запущенном приложении**; первым внутри канала уходит
ближайший по дате, просроченный публикуется сразу обычным сообщением.

**Пакетная отправка** ([ADR-0015](../02-architecture/decisions/0015-batch-publishing.md))
живёт на своём экране «Пакет» (ADR-0032): он собирает черновики из всех
видео готовой папки и раскладывает их время по стратегии (стандартные времена канала,
«каждый день/раз в N дней в ЧЧ:ММ», «каждые N часов», «сейчас»);
занятые слоты — совпадение по минуте с существующими отложками канала
(`PostsService.scheduled_times`) — пропускаются. Отложки читают
исполнители пула ([ADR-0036](../02-architecture/decisions/0036-executor-dispatch-and-urgency.md)):
в канале один, по диспетчеру (отложки там общие для админов),
в группе — все состоящие пользователи, потому что каждый видит только
свои, а лимит в 100 у чата один; так же считает слоты и дозор очереди
отправки. Каждая строка
правится до постановки, дальше — та же очередь и то же серверное
хранение отложек.

## Устройство

- `engine/services/posts.py` — `list_scheduled`, `scheduled_draft`,
  `edit_scheduled`, `send_scheduled_now`, `delete_scheduled`,
  `ScheduledRef`/`ScheduledPostDto`/`ScheduledDraft`, `ScheduledGoneError`.
- `engine/telegram/mtproto.py` — `get_scheduled`, `get_scheduled_message`,
  `edit_scheduled`, `send_scheduled_now`, `delete_scheduled`,
  `media_kind_of` (вид вложения по типам Telethon).
- `ui/pages/publish_section.py` — экраны раздела (`StagePage` — правило
  «виден — работает», `QueueStagePage`, `ScheduledStagePage`,
  `PublishSection` — переходы); `ui/pages/publish_stages.py` — словарь
  стадий (порядок, подписи, подсказки, значки).
- `ui/pages/scheduled_view.py` — вид списка отложенных (`ScheduledView`,
  `unread_text`); `ui/pages/scheduled_panel.py` — панель отложенных
  (`ScheduledPanel`, правило показа `apply_scheduled_view`, слияние
  `merge_community`); `ui/pages/scheduled_edit.py` — форма правки.
- `ui/pages/publish_queue_view.py` — вид списка очереди (`QueueView`,
  `apply_view`); `ui/pages/queue_panel.py` — панель очереди (показ);
  `ui/queue_watcher.py` — наблюдатель очереди (подписка на движок,
  снимок, зрители, завершённые, занятость; ADR-0034).
- Общие слои — `ui/pages/card_list.py` (список карточек),
  `ui/pages/list_view.py` (сортировки, фильтры, страницы, `ViewBar`,
  `PagerRow`).
- Та же панель отложенных работает на вкладке «Отложено» страницы
  сообщества — компактными карточками ([communities.md](communities.md)).

## Будущее

- Замена вложения у отложенной записи — как задание очереди
  с прогрессом (ADR-0028, альтернативы), если понадобится.
- APScheduler ([ADR-0004](../02-architecture/decisions/0004-apscheduler-tasks.md))
  вернётся в проект вместе с регулярными задачами парсинга источников —
  к публикации постов он отношения больше не имеет.
