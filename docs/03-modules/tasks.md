# Модуль «Задачи сообщества»

> Статус: 🟢 реализовано (этапы A–E) · Обновлено: 2026-09-22 · Владелец: olegosx
>
> Решения — [ADR-0038](../02-architecture/decisions/0038-community-tasks.md)
> (задачи, запуски, журнал, расписание), [ADR-0026](../02-architecture/decisions/0026-community-maintenance.md)
> (два вида уборки: правила и границы), [ADR-0039](../02-architecture/decisions/0039-reactions-task.md)
> (реакции) и [ADR-0040](../02-architecture/decisions/0040-join-requests-task.md)
> (приём заявок). До 2026-09-22 модуль назывался
> «Обслуживание сообществ».

## Назначение

Работа, которую приложение делает в сообществе по поручению человека —
по кнопке или по расписанию: уборка в ленте и в участниках, а следом
реакции и приём заявок. Три слова модуля:

- **Задача** — сохранённая настройка сообщества: вид, параметры,
  расписание, включена ли. Одна на вид в каждом сообществе, заводится
  при первом обращении к виду с умолчаниями.
- **Запуск** — одно выполнение задачи: кто запустил (человек или
  расписание), чьими руками шла работа, когда началось и кончилось,
  чем кончилось, отчёт и события. Журнал запусков — тот самый
  «мини-лог по каждой задаче в каждом сообществе».
- **Задание** — элемент очереди каркаса ([ADR-0025](../02-architecture/decisions/0025-job-queue-framework.md)),
  который несёт запуск, пока тот выполняется.

## Виды задач

### Служебные записи

Строки в ленте, которые создал не автор, а сам Telegram: вместо текста
у них поле «действие». Видов действий в схеме Telegram больше
шестидесяти, и они постоянно прибавляются, поэтому модуль сводит их
в **шесть видов** (`ServiceMessageKind`) — человек выбирает, что убрать,
именно видами:

| Вид | Что входит |
|---|---|
| **Участники** | вступления, уходы, вход по ссылке, одобренные заявки |
| **Закрепления** | сообщение закреплено |
| **Оформление** | название, аватар, тема оформления, обои, таймер автоудаления |
| **Видеочаты** | видеочат начался, кончился, запланирован, приглашение |
| **Прочее служебное** | всё остальное: подарки, бусты, платежи, опросы, и любое незнакомое действие — новые виды Telegram не теряются молча |
| **Защищённые** | см. ниже — не удаляются никогда |

**Защищённые записи** — это корневые сообщения тем форума, создание
сообщества, переезд группы в супергруппу и передача владения. Тему
форума Telegram отождествляет с её корневым сообщением: его
идентификатор и есть идентификатор темы, на него отвечает публикация
в тему (ADR-0021). Удалив корень, мы разрушили бы саму тему и осиротили
бы посты очереди, адресованные ей. Отсев защищённых — правило движка
(`selectable_kinds`), а не интерфейса: запуск по расписанию подчиняется
ему так же.

**Параметры задачи:** глубина просмотра (по умолчанию 2000 последних
сообщений — два десятка запросов к Telegram), виды к удалению
и потолок удаления за проход (по умолчанию 500, минимум 1).

**Запуск «без изменений» (просмотр).** Движок читает историю страницами
по сто сообщений от новых к старым и считает служебные записи по видам.
Ничего не меняется. Отчёт: сколько чего нашлось, сколько сообщений
просмотрено, до какого числа дошли и кончилась ли история. Признак
«история кончилась» — **пустая страница** (или запись номер 1): короткая
страница концом не считается — Telegram отдаёт меньше запрошенного
и в середине истории, а Telethon выбрасывает пустышки.

**Обычный запуск (чистка).** Движок проходит историю снова и удаляет
записи выбранных видов пачками. Отчёт: сколько удалено, сколько
Telegram отказался удалять, остановилась ли чистка о потолок за проход.
Серверного фильтра «только служебные» у Telegram нет — история читается
целиком, отбор идёт у нас, цена прохода линейна по длине истории;
отсюда обе границы.

### Удалённые аккаунты

«Удалённый аккаунт» — учётка, которую владелец удалил; в списке
участников она остаётся мёртвой душой. **Параметр задачи** — потолок
исключений за проход (по умолчанию 20, минимум 1): число участников
видно всем, и резкое падение бьёт по охватам сообщества — уборка идёт
порциями, размер которых выбирает человек.

- **Запуск «без изменений»** — «Найти удалённые аккаунты»: никого
  не трогает и отвечает числом. **Обычный запуск** — «Исключить
  удалённые»: убирает не больше потолка.
- **Исключение — это блокировка со снятием**, иначе учётка осела бы
  в списке заблокированных. Ссылка на участника несёт хеш доступа
  (`DeletedAccount`): без него Telegram пользователя не опознаёт,
  а кеш клиента живёт в памяти сессии.
- **Отказ по одной учётке — пропуск, а не конец запуска**; отчёт
  называет число отказов.
- **Чистка убирает за собой.** В супергруппе каждое исключение
  порождает служебную запись «X удалил Y»; записи удаляются одной
  пачкой в конце прохода, а без права удалять сообщения остаются —
  отчёт говорит сколько.
- **Предел выдачи.** Если список кончился раньше заявленного числа
  участников, отчёт скажет прямо: «дальше Telegram список не отдаёт».
- Итог прохода (найдено, исключено, когда) уходит крючком в кэш
  статистики — «Обзор» показывает его среди плиток (ADR-0027).

### Реакции ([ADR-0039](../02-architecture/decisions/0039-reactions-task.md))

Выбранные пользователи пула по очереди ставят реакции записям.
**Один запуск — проход одного пользователя**; кто следующий, помнит
курсор задачи; пауза между проходами — интервал расписания (по умолчанию
случайно 35–96 мин).

**Параметры:** пользователи (из пула, с правом реагировать —
действие `REACT`: администратор всегда, участник по разрешению
«реакции»); набор реакций с весами в процентах — только разрешённые
в сообществе, с описаниями Telegram (веса относительные, 0 — не
выпадает); охват — все записи без реакции пользователя (умолчание),
последняя запись, N случайных; глубина просмотра (256) и потолок
реакций за проход (256); пауза между реакциями случайно в промежутке
(0,7–1,5 с); «Premium ставит две реакции» — две разные из набора.

**Проход:** перечень реакций сообщества сверяется (запрещены —
ошибка запуска; не из перечня — выбрасываются с записью в журнал),
лента читается на глубину страницами по сто (свои реакции —
по `chosen_order`, при флаге `min` дочитываются), записи отбираются
по охвату (со своей реакцией не берутся: новая заменила бы её),
на каждую ставится случайная реакция по весам с паузой между
записями. Отказ Telegram по записи — пропуск; флуд-лимит — конец
прохода. Отчёт: просмотрено, подходящих, поставлено (по эмодзи),
пропущено, кто ставил. **Подобрать записи** — запуск «без изменений»:
считает подходящие, реакций не ставит.

**Названный, но неспособный сейчас пользователь** (приостановлен,
вышел, лишён права) пропускается — очередь идёт к следующему;
неспособны все — отказ при постановке. Реакции ставятся
с `add_to_recent = false`: панель быстрых реакций человека в его
клиенте задача не меняет.

### Приём заявок ([ADR-0040](../02-architecture/decisions/0040-join-requests-task.md))

Разбирает ожидающие заявки на вступление. **Параметры:** отклонять
удалённые аккаунты (умолчание — да; иначе они остаются без решения),
принимать с полным ограничением при ссылке в описании профиля,
то же при канале в профиле (стоит запроса на заявителя — отдельный
флажок), потолок за проход (50). Ограничение прав есть только у групп:
в канале флажки неактивны, заявки принимаются как есть.

**Проход:** страницы ожидающих (описание профиля приходит вместе
с заявкой, карточка заявителя — с хешем доступа); по каждой — удалён →
отклонить, иначе одобрить, затем в группе при ссылках — полное
ограничение (все запреты, кроме бана, бессрочно). Заявку одобряет
и ограничивает один исполнитель: администратор с правом приглашать,
при включённом ограничении — ещё и с правом исключать. Отказ по заявке
(уже разобрана, заявитель негоден) — пропуск; флуд-лимит — конец
прохода. **Посмотреть заявки** — запуск «без изменений»: считает
решения, Telegram не трогает. Ссылка в описании — чистая
`profile_has_links` (адрес, `t.me`, домен, `@упоминание`).

## Как идёт запуск

1. **Постановка.** Кнопка раздела сохраняет параметры формы в задачу
   и ставит запуск (`run_now`); параметры проверяются под этот запуск
   (чистке нужен хотя бы один вид записей, просмотру — нет). Способный
   исполнитель ищется в пуле сразу: отказ «некому» звучит при нажатии,
   а не через час в журнале.
2. **Очередь.** Задание встаёт в очередь задач с несколькими слотами
   (`PARALLEL_TASKS`, 3): задачи разных сообществ идут одновременно,
   в одном сообществе — не больше одной (замок задания). Темп внутри
   аккаунта держит дорожка ([ADR-0024](../02-architecture/decisions/0024-telegram-account-lane.md))
   с приоритетом `MAINTENANCE`: ниже действий человека на экране
   и срочной публикации, выше фоновых чтений. Между страницами дорожка
   пропускает вперёд публикацию.
3. **Исполнитель выбирается в момент запуска** — способных даёт
   диспетчер ([ADR-0036](../02-architecture/decisions/0036-executor-dispatch-and-urgency.md))
   по хранимому снимку прав и живой занятости дорожек (свободный
   раньше занятого загрузкой, при равенстве — публикатор по умолчанию),
   а кого из них взять, решает вид (`choose_executor`): уборка —
   первого, реакции — следующего по кругу из названных.
   Права у видов разные: чтение истории и участников — любой состоящий
   пользователь; удаление записей — «удалять сообщения»; исключение —
   «блокировка пользователей». Ни одно не следует из другого. Строкам
   без снимка прав (пережившим миграцию) права уточняются живым зондом
   один раз. Только пользователи: Bot API не отдаёт ни списка
   участников, ни чужой истории.
4. **Строка журнала заводится в начале** запуска со значением «идёт»
   и дописывается в конце крючком записи исхода каркаса — до того, как
   новый статус виден в памяти. Исходы: готово · ошибка · отменено
   (человеком) · прервано остановкой движка. Флуд-лимит прекращает
   запуск целиком (ADR-0017): исход «ошибка» с причиной, неполный отчёт
   не сохраняется — «не получилось» честнее правдоподобной неправды
   о числах; события запуска при этом остаются (в том числе строка
   «просмотрено N, удалено M») — след для разбора.
5. **Отмена** срабатывает между страницами: рвать обращение к Telegram
   посреди удаления незачем. Удаление сообщества снимает его задания:
   задание держит снимок сообщества и работает по его `tg_chat_id`,
   от строки в базе не завися; задачи и журнал уходят каскадом.

## Расписание

Задача может запускаться сама (`Schedule`, `engine/tasks/schedule.py`):

- **только по требованию** — расписания нет;
- **с интервалом** — пауза между запусками от min до max минут,
  случайно в промежутке (равные границы — постоянный интервал;
  пределы — от минуты до недели);
- **в моменты суток** — список «ЧЧ:ММ» по местному времени
  (формат тот же, что у времён публикации).

Следующий момент **хранится** в задаче (`next_run_at`) и назначается
заново после конца **любого** запуска — по кнопке или по расписанию:
пауза между проходами считается между ними, а случайная длина
вытягивается один раз, и перезапуск приложения ничего не сдвигает.
Включение проверяет сохранённые параметры под обычный запуск: чистка
без выбранных видов записей отклоняется при сохранении. Включить
«только по требованию» нельзя.

**Планировщик** — одна периодическая задача движка с тиком в минуту
(`TasksService.run_due`): берёт включённые задачи с наступившим сроком,
пропускает выключенные сообщества и задачи, у которых задание уже идёт
или ждёт, ставит запуск с признаком «по расписанию». Пропущенные
за время выключения приложения запуски догоняются один раз. Ошибка
запуска по расписанию **не остаётся карточкой** в панели хода работы:
её «повтор» — следующий срок, а причина — в журнале. Тот же тик раз
в сутки убирает журнал старше 90 дней. Останавливается первым, до
очереди.

**Подтверждение при включении** (ADR-0038, п. 5): для ручного запуска
правило «сначала показать, потом удалить» действует как прежде; при
включении расписания чистки диалог один раз перечисляет виды записей
и предел за проход — каждый запуск удалит не больше него без
дополнительного вопроса.

## Интерфейс

Вход — вкладка «Задачи» на странице сообщества, пункт меню «…» в её
шапке и кнопка «Задачи» на карточке дашборда (у групп и у выключенных
сообществ) — то же тело в рабочем окне. У сообщества без
userbot-публикатора вкладка остаётся, но вместо формы — объяснение
и переход в «Участники».

Тело (`TasksPanel`, `ui/pages/tasks.py`; спека —
`_misc/mockups/design_handoff/screens/tasks.md`) — **два вида**:

**Обзор** — карточка на каждую доступную задачу (`FlowGrid`, минимум
340). На карточке: название, суть одной строкой, тумблер
«по расписанию», строка расписания («каждый день в 04:00», «каждые
30–60 мин · следующий в 14:42», «по требованию») и строка итога
последнего запуска («последний: сегодня 04:00 · удалено 132»;
у ошибки — плашка и причина). Кнопок нет: карточка кликабельна
целиком, а тумблер спрашивает подтверждение при включении. Пока
задача работает, строку расписания заменяет полоса хода. Какие задачи
доступны, решает `available_kinds`: «Удалённые аккаунты» — только
у групп, остальные три — у обоих видов (в канале «Приём заявок»
принимает заявки как есть, ограничивать права там нечем).

**Настройка одной задачи** — строка пути «Задачи › название», шапка
(название, суть, запуск «без изменений» и настоящий), полоса хода
с «Отменить» на время работы, строка ошибки последнего запуска
(`InfoBar` с переходом туда, где её чинят, — правило
`error_fix_target`), блоки параметров формой «подпись — поле»
(колонка подписей 220, поля своей ширины), блок **«Расписание»**
(включено, как часто, границы или моменты суток; поля лишнего вида
скрыты), **одна кнопка «Сохранить»** на параметры и расписание
(`save_task` движка — одной записью, `form_dirty` держит кнопки
неактивными, пока форма совпадает с сохранённым; вопрос о расписании
задаётся только при его включении) и **три последних запуска** таблицей
со ссылкой «Весь журнал…» на прежнее окно журнала (итог с ошибкой —
цветом ошибки). Уход с несохранёнными правками — путь «Задачи», другая
вкладка страницы, другое сообщество — спрашивает «Сохранить / Не
сохранять / Отмена» (`ask_save_changes`); «Сохранить» уводит только после
ответа движка, «Отмена» оставляет всё на месте. Свежий снимок сообщества
открытую настройку с правками не пересобирает.

Блоки по видам: **«Служебные записи»** — «Что удалять» строками видов
с числами из последнего просмотра (табличные цифры; числа берутся
из отчёта последнего просмотра в журнале — `last_scan`, поэтому
переживают перезапуск; защищённый вид без флажка, с объяснением) и «Границы» (глубина, предел за проход);
**«Удалённые аккаунты»** — одна граница «исключать за проход
не больше»; **«Реакции»** — «Кто ставит» таблицей на модели
(`TableView` + `QAbstractTableModel` + `QSortFilterProxyModel`: поиск
по имени, отбор «все / отмеченные / могут ставить», сортировка
по колонкам, шесть строк и дальше прокрутка; правило отбора —
`reactor_matches`), «Какие реакции и их вес» плитками постоянной
ширины 150 и «Каким записям» (охват, глубина, потолок, паузы,
Premium); **«Приём заявок»** — «Правила» тремя флажками (у канала
ограничения неактивны) и «Границы».

Ход работы приходит от наблюдателя очереди задач (ADR-0034) прямо
в карточки и в настройку — общей панели очереди на вкладке больше нет.
Окно задач с дашборда — та же панель в прокрутке; кнопка «Участники…»
в строке ошибки закрывает окно и открывает окно исполнителей.
Задание, остановившееся на ошибке, снимается с очереди: причина уже
записана в журнал запусков и видна строкой ошибки.

## Устройство

- `engine/tasks/` — виды задач по одному контракту `TaskSpec`
  (`model.py`): параметры с проверкой и переводом в JSON, нужное право,
  выполнение шагами, отчёт с переводом в JSON и итогом одной строкой.
  `service_messages.py`, `deleted_accounts.py` — два вида уборки
  (правила, границы, отчёты и их тексты — чистые функции,
  `service_summary` / `members_summary` / `kind_title`); реестр видов
  `SPECS` — в `__init__.py`.
- `engine/tasks/reactions.py` — вид «реакции»: параметры, отчёт,
  чистые `pick_reaction` / `pick_reactions` / `select_targets` /
  `next_user` / `rotation`, проход.
- `engine/tasks/join_requests.py` — вид «приём заявок»: параметры,
  отчёт, чистая `profile_has_links`, проход с решением по заявке.
- `engine/tasks/schedule.py` — `Schedule`, `ScheduleKind`, чистая
  `next_run`, `schedule_text` (без сети, базы и интерфейса).
- `engine/services/tasks.py` — `TasksService`: строка задачи (`task`,
  `list_tasks`, `save_params`, `save_schedule`, `save_task`), запуск по требованию
  (`run_now` с признаком `dry_run`), планировщик (`start_scheduler`,
  `run_due`, `prune_runs`), журнал (`runs`), очередь на каркасе
  (`state`, `cancel`, `retry`, `dismiss`, `subscribe`), снятие заданий
  удалённого сообщества (`drop_community`). Строки: `community_tasks`,
  `task_runs` ([модель данных](../05-data/data-model.md)).
- `engine/telegram/mtproto.py` — `service_message_kind` (перевод
  действия Telegram в вид — чистая функция), чтение страницы истории,
  удаление пачки, страница участников, исключение; реакции —
  `available_reactions`, `reactions_page`, `send_reaction`; заявки —
  `join_requests_page`, `handle_join_request`, `restrict_fully`,
  `has_personal_channel`.
- `engine/telegram/types.py` — типы границы: `ServiceMessageKind`,
  `ServiceMessageInfo`, `ServiceMessagesPage`, `DeletedAccount`,
  `ParticipantsPage`, `ChatReactions`, `ReactionOption`, `ReactablePost`,
  `ReactionsPage`, `JoinRequest`, `JoinRequestsPage`. Сырые объекты
  Telethon до сервисов не доезжают.
- `ui/pages/tasks.py` — `TasksPanel` (вкладка и тело окна `TasksDialog`),
  разделы видов, `TaskRunsDialog` (журнал); тексты журнала —
  чистые функции (`run_kind_text`, `run_result_text`, `run_events_text`).
