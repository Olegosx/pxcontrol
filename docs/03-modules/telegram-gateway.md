# Модуль «Шлюз Telegram»

> Статус: 🟢 реализовано (в объёме текущих функций) · Обновлено: 2026-09-22 · Владелец: olegosx

## Назначение

Единая точка взаимодействия с Telegram **поверх двух транспортов** — Bot API
и MTProto ([ADR-0007](../02-architecture/decisions/0007-hybrid-botapi-mtproto.md)).
Весь остальной код обращается к Телеграму только через этот модуль
(`TelegramGateway`) и не знает, какой транспорт использован.

## Флуд-лимиты и клиент Telethon

Клиент создаётся с порогом автосна `flood_sleep_threshold = 0`
(2026-09-22, ADR-0038 этап E): по умолчанию Telethon сам молча ждёт
внутри запроса при лимите короче 60 с, и дорожка аккаунта (ADR-0024)
с учётом активности (ADR-0030) о нём не узнавали. Теперь любой
флуд-лимит приходит исключением `FloodWaitError` → `UserbotFloodError`,
и заморозку назначает дорожка.

## Роли транспортов ([ADR-0011](../02-architecture/decisions/0011-publish-via-userbot.md))

- **MTProto** (`Telethon`, userbot-аккаунты) — **публикация всего
  контента** (`publish`: текст/фото/видео/аудио/документ, сразу или
  отложенно через `schedule_date`; при лице «сообщество» в группе —
  с явным `send_as` самим чатом, ADR-0036), чтение отложенных (`get_scheduled`)
  и **действия над отложенными на сервере** (2026-09-15, по
  core.telegram.org/api/scheduled-messages): чтение одной записи
  целиком (`get_scheduled_message`, `messages.getScheduledMessages`),
  правка текста и времени (`edit_scheduled` — `messages.editMessage`
  с `schedule_date`; ответ «ничего не изменилось» — не сбой),
  «опубликовать сейчас» (`send_scheduled_now`,
  `messages.sendScheduledMessages`) и удаление без публикации
  (`delete_scheduled`, `messages.deleteScheduledMessages` — обычное
  удаление сообщений для очереди отложенных не годится: у неё свои id
  и свой метод). Вложение и тема правкой не меняются: у метода нет
  адресата темы, а замена файла — загрузка с прогрессом, то есть
  задание очереди, а не правка;
  в будущем — чтение каналов-источников. Аккаунтов может быть несколько
  (ADR-0019): шлюз держит **пул клиентов** «id аккаунта → транспорт»,
  userbot-операции адресные (параметр `account_id` — аккаунт,
  привязанный к каналу); Premium и флуд-лимиты — пер-аккаунтные.
  Все аккаунты с сессиями подключаются при старте движка и сразу после
  входа; повторная активация аккаунта (`activate_userbot`) закрывает
  его прежнего клиента и применяет новые реквизиты — повторный вход
  после отзыва сессии работает без перезапуска.
  Неудача подключения (нет сети, сессия отозвана) не мешает запуску
  приложения. Потерянное соединение чинится **по требованию**: перед
  операцией транспорт проверяет `is_connected()` и переподключается
  (Telethon, исчерпав свои попытки, остаётся отключённым насовсем —
  без этого разовый обрыв сети требовал бы перезапуска приложения);
  сессия при этом перепроверяется — отзыв за время простоя виден сразу.
  Тот же ремонт покрывает **запуск без сети** (2026-08-15): клиента ещё
  нет, но реквизиты сохранены — первая операция сама повторяет `start()`
  под общим замком, перезапуск приложения не нужен.
  При каждом подключении читается **статус Premium** аккаунта
  (`get_me`): от него зависит лимит на файл — точные значения
  в `telegram/types.py` (`userbot_max_file_bytes`: 4000 частей
  по 512 КиБ = 2000 МиБ, с Premium 8000 = 4000 МиБ; «круглые» 2 ГиБ
  чуть больше настоящего лимита). Статус виден на карточке аккаунта
  и в подсказке «Публикации»; сбой запроса — статус False (меньший,
  безопасный лимит).
- **Статистика (ADR-0027).** Userbot читает встроенную статистику
  Telegram (`_fetch_stats` — выбор метода по виду сообщества, как
  в `client.get_stats` Telethon, но дата-центр из ошибки миграции
  `STATS_MIGRATE` возвращается наружу: графики «по токену» догружаются
  через тот же одолженный канал — домашний дата-центр отвечает
  на чужой токен не миграцией, а `GRAPH_INVALID_RELOAD`, ловилось
  живьём; не догрузившийся график — пустой ряд, а не срыв прохода) —
  `userbot_community_analytics`;
  ответ разбирается в собственный тип `CommunityAnalytics`, JSON
  графиков — чистой функцией `stats_graph.parse_graph`. Берётся **всё,
  что отдаёт ответ** (`BroadcastStats` / `MegagroupStats`): пары
  «сейчас, раньше» по именам полей (подписчики, просмотры / пересылки /
  реакции на пост и на историю, сообщения / читающие / пишущие группы),
  доля включённых уведомлений, все графики по дням с именами рядов
  Telegram (`NamedSeries`: взаимодействия, Instant View, звук,
  истории, сообщения, действия), графики долей суммой за период
  (`Share`: источники просмотров и участников, языки, реакции
  по эмодзи, дни недели — «пирог» без оси разбирается порядковыми
  моментами), недавние посты (`RecentPost`: просмотры, пересылки,
  реакции) и списки самых активных (`TopPoster`/`TopAdmin`/
  `TopInviter`, имена — из `users` ответа). Каждый график «по токену» —
  отдельное обращение через дорожку; проход раз в 6 часов это терпит. Признак
  доступности (`can_view_stats`) и связанный чат приходят в том же
  `channelFull`, что и участники с онлайном (`userbot_community_stats`);
  крайние точки истории (последний пост, создание) —
  `userbot_history_marks`. Все три — фоновый приоритет дорожки.
- **Bot API** (`aiogram`, по токену на операцию, без постоянного
  соединения) — проверка токена (`getMe`), проверка сообщества и прав
  бота в нём (`getChat`/`getChatMember`) — **фактом, а не приговором**:
  возвращается участие и полный снимок прав (ADR-0035, п. 7), а «может
  ли бот публиковать» решает правило над снимком; отказ остаётся там,
  где Telegram не показал сообщество боту, диагностика «где состоит бот»
  (`getUpdates`), дешёвый частый опрос статистики — участники
  и связанный чат (`bot_community_stats`: `getChat` +
  `getChatMemberCount`; бот-путь дорожкой не регулируется, поэтому
  загрузки userbot ему не мешают — ADR-0027) и **запасной транспорт
  публикации** для каналов без
  userbot-админа: `bot_send_text` и `bot_send_media` (текст и медиа
  до 50 МБ, только «сейчас»). Обе отправки несут **клавиатуру**
  (ADR-0031): кнопки ставит только бот, и своему посту он ставит их
  сам, одним вызовом. Отдельно — `bot_edit_markup`: так бот дорисовывает
  кнопки к посту публикателя (в канале, если у него есть право изменять
  сообщения) и снимает их. Перевод нашей клавиатуры в формат Bot API —
  `bot_api.to_reply_markup`; сам тип клавиатуры к транспортам
  не привязан (`telegram/markup.py`). Маршрутизация — в `PostsService`
  по чистой лестнице `publish_route.choose_route`.

Публикация через userbot (`publish`) возвращает **номер отправленного
поста** (у отложенного — номер записи в очереди отложенных сервера):
по нему бот и дорисовывает кнопки.

## Реакции ([ADR-0039](../02-architecture/decisions/0039-reactions-task.md))

Три userbot-операции для задачи реакций, все с приоритетом
`MAINTENANCE`: `userbot_available_reactions` — режим и перечень
разрешённых реакций сообщества с описаниями (`channels.getFullChannel`
→ `available_reactions` плюс глобальный `messages.getAvailableReactions`
без неактивных; кастомные эмодзи не отдаются); `userbot_reactions_page`
— страница ленты без служебных записей с реакциями текущего аккаунта
(`chosen_order`; при флаге `min` дочитываются
`messages.getMessagesReactions` по номерам страницы — второй запрос
в том же обращении); `userbot_send_reaction` — `messages.sendReaction`
списком `ReactionEmoji`, `add_to_recent=False`. Отказы по записи
(`REACTION_INVALID`, `REACTIONS_TOO_MANY`, `PREMIUM_ACCOUNT_REQUIRED`)
переводятся в `UserbotReactionError` — пропуск записи, а не сбой.

## Заявки на вступление ([ADR-0040](../02-architecture/decisions/0040-join-requests-task.md))

Четыре userbot-операции задачи приёма заявок, приоритет `MAINTENANCE`:
`userbot_join_requests_page` — страница ожидающих
(`messages.getChatInviteImporters` с `requested`; первая страница —
пустое смещение, дальше — «дата + заявитель» последней заявки, хеши
заявителей запоминаются на время запуска; описание профиля приходит
полем `about`, удалённость и хеш доступа — из `users`);
`userbot_handle_join_request` — `messages.hideChatJoinRequest`
с `approved`; `userbot_restrict_fully` — `channels.editBanned` со всеми
запретами, кроме `view_messages` (бан), без срока;
`userbot_has_personal_channel` — `users.getFullUser` →
`personal_channel_id`. Отказы по заявке (`HIDE_REQUESTER_MISSING`,
`USER_ALREADY_PARTICIPANT`, `INPUT_USER_DEACTIVATED`,
`USER_CHANNELS_TOO_MUCH`) — `UserbotJoinRequestError`, пропуск.

## Дорожка аккаунта ([ADR-0024](../02-architecture/decisions/0024-telegram-account-lane.md))

Единица дефицита в Telegram — **аккаунт**: его нельзя дёргать
параллельно, нельзя опрашивать быстрее некоторого темпа, а флуд-лимит
(«подождите N секунд») сервер назначает аккаунту целиком. Поэтому рядом
с пулом транспортов шлюз держит пул **дорожек** — по одной на аккаунт
(`lane.py`, `AccountLane`). Все userbot-операции идут по дорожке своего
аккаунта, и она отвечает за четыре вещи:

- **очередь** — операции аккаунта не выполняются параллельно;
- **зазор** между запросами — `DEFAULT_MIN_INTERVAL_S` = 0,3 с
  (около трёх запросов в секунду; отсчитывается от конца обращения).
  Редкой операции зазор незаметен — он срабатывает на запросах подряд,
  то есть в массовых проходах, ради которых и заведён;
- **приоритет** — кто из ожидающих пойдёт следующим. Задаёт его сам
  шлюз, по назначению операции, а лестница выстроена **по срочности**
  ([ADR-0036](../02-architecture/decisions/0036-executor-dispatch-and-urgency.md),
  2026-09-21): `INTERACTIVE` (человек ждёт ответа: проверка доступов,
  список тем), `PUBLISH_DUE` (срочная публикация: пост «сейчас», догон
  просроченного, режим «кнопки важнее», дорисовка кнопок к только что
  вышедшему посту), `MAINTENANCE` (чистка служебных записей и удаление
  мёртвых аккаунтов, ADR-0026), `BACKGROUND` (статистика, расписание,
  дозор слотов), `PUBLISH_PLANNED` (отложенная запись с датой
  в будущем). Довод: загрузка файла — единственная долгая операция,
  всё остальное — секунды; «короткое вперёд длинного» даёт наименьшее
  суммарное ожидание, а плановая загрузка не голодает — коротких
  ожидающих конечное число. Срочность публикации шлюз выводит сам
  из момента поста (`publish_priority` ← `urgency` в `types.py`);
  посты бота всегда срочные — отложек у ботов не бывает. Вызывающему
  указывать приоритет не нужно;
- **заморозка** — пойманный флуд-лимит останавливает обращения
  к аккаунту до названного сервером срока, и это знание общее:
  следующая операция узнаёт о лимите из отказа, не тревожа Telegram
  (настойчивость сроки удлиняет), и знание переживает проход —
  своих списков «провинившихся аккаунтов» сервисы больше не ведут.

Дорожка **не ждёт за вызывающего**: вместо молчаливой паузы наружу
уходит `UserbotFloodError` с остатком срока (перевод из общего
`TelegramFloodError` делает шлюз — потребители разбирают исходы
по таксономии userbot). Кто умеет ждать — очередь отправки — ждёт сам,
своим прерываемым ожиданием (ADR-0020); фоновые чтения пропускают
аккаунт до следующего прохода. Подключение и отключение аккаунта
дорожкой не регулируются: она про поток запросов, а не про соединение,
и переживает замену транспорта — заморозка принадлежит аккаунту
Telegram, а не нашей сессии.

Боты тоже на дорожках (ADR-0030, 2026-09-15): ключ пула — исполнитель
(`ExecutorRef` из `telegram/types.py`: пользователь или бот, и id; до сверки
ADR-0035 звался `LaneOwner`), бот-методы адресуются `BotRef`
(id + токен). Дорожка бота без зазора (`BOT_MIN_INTERVAL_S` = 0: лимиты
Bot API щедрые и пер-бот), но с очередью, приоритетом и той же
заморозкой после `RetryAfter` — прежде отказ «подождите N секунд» у бота
никого не останавливал. Без дорожки осталась одна операция — проверка
токена при добавлении бота: бота в приложении ещё нет.

## Учёт активности ([ADR-0030](../02-architecture/decisions/0030-account-activity.md))

Каждое выполненное тело `slot` дорожки — запись `OperationRecord`:
владелец, **вид работы** (`WorkKind`: публикация, действие человека,
обслуживание, фон — у обоих приоритетов публикации вид один, иначе
графики по видам раздвоились бы), начало и конец, исход (успех, ошибка,
флуд-лимит со сроком, отмена). Отказ до тела (заморозка) не пишется —
Telegram не тревожили. Записи копятся в **журнале операций** шлюза —
объекте `OperationLog` (`telegram/lane.py`), а не в голом списке:
дорожка получает журнал один раз и держит ссылку всю свою жизнь,
поэтому выемка (`drain_operations` / `restore_operations`) опустошает
журнал **на месте** и никогда не подменяет его новым. Правило живёт
в типе: списка снаружи просто нет. Пока его не было, первая же выемка
делала все созданные до неё дорожки немыми до перезапуска приложения,
и страница исполнителя показывала ноль операций при круглосуточной
работе (исправлено 18.09.2026). Переполнение журнала (`LOG_CAPACITY`,
случается только при подряд отказывающем хранилище) вытесняет самые
старые записи и сообщает об этом в журнал приложения. Живое состояние дорожек
(чем занята, сколько ждут, заморозка) отдаёт `live_states`. Хранение
и чтение — сервис активности (`engine/services/activity.py`, таблица
`account_operations`): сброс пачкой раз в десять секунд и при остановке,
занятость окна — пересечением интервалов при чтении, хранение год.

## Приостановленные аккаунты ([ADR-0029](../02-architecture/decisions/0029-users-and-bots-section.md))

Рядом с пулами шлюз держит набор **приостановленных** аккаунтов
(`pause_userbot` / `resume_userbot` / `userbot_paused`). Пауза закрывает
транспорт аккаунта, а любое обращение к нему — ещё до дорожки — получает
`UserbotPausedError`: наследник «не подключён», поэтому очередь отправки,
фоновые чтения и зонды прав ведут себя как при обрыве связи, а текст
зовёт не войти, а возобновить в разделе «Пользователи и боты». При старте
приостановленные регистрируются, но не подключаются (сервис аккаунтов);
`deactivate_userbot` пометку снимает — удалённый аккаунт покидает
приложение целиком, и SQLite может отдать его id следующей записи.
Снимок состояния соединения для показа — `userbot_connected`
(`MtprotoTransport.connected`, без запросов к Telegram).

## Устройство

- `gateway.py` — фасад `TelegramGateway`; сервисы объявляют узкие
  протоколы нужной им части (разделение интерфейсов). **Имена**:
  методы бот-пути начинаются с `bot_`. До 2026-09-12 часть из них
  звалась без пометки (`send_text`, `check_community`), и по вызову
  в сервисе нельзя было понять, основной это путь или запасной, —
  при разных лимитах и разных возможностях.

  С 18.09.2026 путь назван префиксом у **обоих**: `bot_` и `userbot_`.
  Так вызов в сервисе сам говорит, кто везёт операцию, — а у путей
  разные лимиты, разные возможности и разная цена отказа. Прежде
  userbot-методы были вперемешку: половина с префиксом, половина без
  (`publish`, `get_scheduled`), один с суффиксом. Имена транспортов
  не меняются: внутри `mtproto.py` префикс лишний — там весь модуль
  и есть userbot.
- `lane.py` — `AccountLane`, `TelegramPriority` (лестница по срочности)
  и `WorkKind` (вид работы для учёта): дисциплина обращений к аккаунту
  (см. раздел выше).
- `types.py` — `OutgoingPost`: единая сущность исходящего поста на
  границе «сервисы → транспорты».
- **Ввод исполнителя** (ADR-0035, только userbot-путь): вступление
  в публичное сообщество (`userbot_join_public` — `channels.joinChannel`),
  вступление по ссылке-приглашению (`userbot_join_by_invite` —
  `messages.importChatInvite`; «заявка отправлена» возвращается
  значением, а не исключением — это исход, а не сбой), чтение основной
  ссылки сообщества (`userbot_invite_link` — поле `exported_invite`
  того же `channelFull`, которым читается статистика; приложение ссылок
  **не создаёт**), приглашение (`userbot_invite_participant` —
  `channels.inviteToChannel`, отказ приходит и исключением, и списком
  «не приглашённых» в ответе — разбираются оба) и назначение
  администратором (`userbot_promote` — `channels.editAdmin`, так бот
  попадает в канал). Все пять — с приоритетом «человек ждёт ответа»
  и только по явному действию человека.
- `rights.py` — снимок прав исполнителя в сообществе (ADR-0035):
  участие (`ParticipantStatus`), 17 флагов администратора и разрешения
  участника, включая реакции. Ограничения Telegram живут двумя слоями —
  личные и общие, — и складывает их **транспорт**, на границе: наружу
  уходит ответ на вопрос «может ли», а не форма ответа сервера. Оба
  перевода (`userbot_rights`, `bot_rights`) чистые, поэтому проверяются
  тестами на настоящих объектах обеих библиотек. До ADR-0035 разбор прав
  жил шестью функциями в двух модулях, и половину прав вычислял только
  один транспорт, а половину — только другой.
- `stats_graph.py` — разбор графиков встроенной статистики Telegram
  (чистые функции, тестируются на записанных ответах).
- `refs.py` — разбор пользовательского ввода «какой канал»
  (`normalize_chat_ref`: @имя, ссылки t.me/…, числовой ID) — общий
  модуль обоих транспортов; ошибка разбора — `ChatRefError`.
- `mtproto.py` — `MtprotoTransport` (публикация, чтение) и
  `MtprotoLoginManager` (пошаговый вход: код → 2FA → строка сессии).
- `bot_api.py` — функции Bot API (aiogram).

## Ссылки на чат и на пользователя (проверено 2026-09-12)

Telegram опознаёт собеседника по паре «идентификатор + хеш доступа».
Хеши живут в кеше клиента, а он **не переживает перезапуск**:
`StringSession` сохраняет только ключ авторизации и адрес сервера.
Отсюда два разных правила, и они не взаимозаменяемы:

- **чат (канал или супергруппа)** — числового идентификатора
  достаточно: не найдя хеш в кеше, Telethon запрашивает
  `channels.getChannels` с нулевым хешем, и сервер принимает такой
  запрос для чатов, где аккаунт состоит. Поэтому все наши операции
  по `tg_chat_id` надёжны и после перезапуска;
- **пользователь** — так не работает: `users.getUsers` с нулевым
  хешем отвечает только про тех, кто в контактах (или писал боту),
  а для остальных возвращает пустую карточку, и Telethon сообщает
  «не могу найти сущность». Значит ссылку на пользователя нужно
  передавать вместе с хешем, полученным в том же ответе, где пришёл
  сам пользователь.

Так устроена чистка удалённых аккаунтов (ADR-0026): список участников
отдаёт и учётку, и её хеш, и дальше они путешествуют вместе
(`DeletedAccount`). Без этого исключение работало бы только в том
запуске, где прошёл поиск, — и падало бы после перезапуска.

**Бот-путь живёт по тому же правилу** (проверено живьём 2026-09-20,
проба `_misc/tg_kicked_bot_probe.py`): по числовому идентификатору
Bot API отвечает только боту, который в сообществе состоит. Чужому
боту приватное сообщество по ID не существует — сервер отвечает 400
«Bad Request: chat not found», а убранному — 403 («bot was kicked from
the channel chat», «bot is not a member of the supergroup chat»).
Попутно подтверждено: снятие бота с администраторов канала само
выводит его из канала — участником он там не бывает. Кода у первого
отказа нет, только описание,
поэтому `_bot_errors` сверяет его по тексту (приём `_MESSAGE_GONE`)
и оба ответа переводит в один класс `BotNotInCommunityError` — факт
участия, по которому перепроверка записывает боту «не состоит»,
а ввод исполнителя (ADR-0035) начинает лестницу. Публичное сообщество
бот видит и по `@имени`, поэтому при подключении по вводу человека
это второй путь, о котором и говорит текст ошибки.

## Ответы библиотеки: чего они не обещают (проверено 2026-09-13)

Сплошная сверка всех обращений к Telethon по её исходникам — после
того как чистка участников упала на неожиданном типе ответа. Что
выяснилось и учтено:

- **Список может прийти без списка.** У ответов «ничего не изменилось»
  (`messages.messagesNotModified`, `channels.channelParticipantsNotModified`)
  полей с содержимым нет вовсе. Мы запрашиваем с нулевым хешем, при
  котором сервер такого не присылает, но читаем ответы через
  безопасный доступ — цена нулевая, а падение было бы в проде.
- **Среди записей бывают пустышки.** Удалённое сообщение приходит
  как `messageEmpty`: идентификатор есть, даты нет. Наш тип границы
  обещает дату, поэтому такие записи отбрасываются в транспорте.
  Иначе `None` доезжал бы до списка отложенных и ронял его сортировку
  далеко от места, где возник.
- **«Кто я» отвечает пустотой**, если сессия не авторизована. Это
  не профиль без имени, а отсутствие ответа: транспорт поднимает
  «сессия недействительна», иначе профиль аккаунта затёрся бы
  пустыми полями.
- **Права администратора у владельца библиотека читает как есть.**
  Её свойства (`delete_messages` и прочие) отвечают ровно то, что
  прислал сервер, — и владельцу с неполным набором флагов скажут
  «нельзя». В Telegram права владельца урезать невозможно, поэтому
  у нас владелец — отдельная ветка (`has_admin_right`), а не частный
  случай чтения флагов. Закреплено тестом на настоящем объекте прав.
- **Бот-путь** (aiogram) устойчив: статусы и права читаются как
  необязательные поля, поэтому разные виды участника
  (владелец, администратор, ограниченный) не ломают проверку.

## Ошибки userbot (таксономия)

Ошибки Telethon переводятся в доменные исключения с понятным текстом;
подклассы `UserbotUnavailableError` разводят причины, потому что сервисы
принимают по ним разные решения:

- `UserbotNotConnectedError` — не подключён / нет связи (временное);
  - `UserbotPausedError` — его подкласс: аккаунт приостановлен
    человеком (ADR-0029, 2026-09-15). Бросает шлюз, не транспорт;
    поведение потребителей — как при обрыве связи, текст — «возобновите»;
- `UserbotSessionExpiredError` — сессия отозвана, нужен повторный вход;
- `UserbotAccessError` — подтверждённый отказ Telegram (в том числе
  `SEND_AS_PEER_INVALID` — от имени группы публиковать не дали:
  у аккаунта нет права «анонимность», ADR-0036): сообщество
  недоступно аккаунту или писать в нём запрещено (`ChatWriteForbidden`).
  С ADR-0035 (п. 7) нехватка прав отказом не является — зонд отдаёт
  снимок, и «может ли» решает правило над ним;
  - `UserbotNotInCommunityError` — его подкласс (ADR-0035): аккаунта
    в сообществе **нет** — выгнали, вышел, закрыли от него
    (`ChannelPrivate`, `UserNotParticipant` вне зонда). Для потребителей
    это по-прежнему подтверждённый отказ, а перепроверка по нему пишет
    исполнителю «не состоит», не оставляя прежний снимок. Внутри зонда
    `UserNotParticipant` до ошибки не доходит — превращается в снимок
    со статусом «не состоит» сам;
- `UserbotScheduleFullError` — все слоты отложек канала заняты
  (`SCHEDULE_TOO_MUCH`; лимит Telegram — 100 на канал). Не ошибка
  доступа: очередь отправки возвращает такой пост в «ждёт слота»
  и выпускает при освобождении слота (ADR-0016, 2026-08-26);
- `UserbotDeleteForbiddenError` — Telegram отказался удалять записи
  (`MESSAGE_DELETE_FORBIDDEN`). Отдельный класс нужен обслуживанию:
  отказ там считается пропуском пачки, а не сбоем прохода (ADR-0026),
  и наружу из `delete_messages` не выходит — операция возвращает
  «удалено 0». Перевод живёт в общем маппере: ветка `except` у самой
  операции не срабатывала бы — маппер переводит раньше (2026-09-12);
- `UserbotMessageGoneError` — записи, к которой обращались, уже нет
  (`MESSAGE_ID_INVALID`): отложка ушла в ленту или удалена из другого
  клиента между чтением списка и действием. Штатная гонка (истина —
  сервер, ADR-0010), а не отказ в правах: сервис постов переводит её
  в `ScheduledGoneError` — сигнал перечитать список (2026-09-15);
- `UserbotInviteLinkError` — ссылка-приглашение недействительна,
  устарела или отозвана (ADR-0035). Отдельный класс: человеку здесь
  нужен не «повтор позже», а другая ссылка;
- `UserbotInviteRefusedError` — Telegram отказал в приглашении
  (приватность приглашаемого, невзаимные контакты, пределы сообщества).
  Отказ не наш и не чинится правами: приглашение потому и последняя
  ступень лестницы ввода;
- `UserbotFloodError` — флуд-лимит «подождите N секунд»
  (всё семейство `FloodError`, назвавшее срок: обычный `FLOOD_WAIT`,
  отдельный лимит на загрузку медиа у не-Premium аккаунта
  `FLOOD_PREMIUM_WAIT` и прочие; распознаются по семейству, а не
  поимённо — бессрочные вроде `FrozenMethodInvalid` срока не называют
  и сюда не попадают, 2026-09-12). Наследует и общий `TelegramFloodError`
  (см. ниже), и `UserbotUnavailableError` — прежние обработчики
  временной недоступности продолжают работать (2026-08-27).
  В этом же классе приходит **отказ дорожки** аккаунта (ADR-0024):
  лимит поймала соседняя операция, срок ещё не вышел, и обращаться
  к Telegram незачем — в `retry_after_s` остаток срока.

Флуд-лимит обоих транспортов сведён в общий класс
`TelegramFloodError` (`engine/telegram/types.py`, поле
`retry_after_s`): Bot API переводит в него `TelegramRetryAfter`,
MTProto — `FloodWaitError`. Очередь отправки по этому классу
не хоронит элемент в ошибке, а ждёт названный сервером срок
и повторяет (2026-08-27).

**Ошибки бот-пути** (уточнено 18.09.2026). Базовая — `BotError`:
Telegram отклонил операцию бота, будь то проверка сообщества при
подключении, отправка или правка клавиатуры. Прежнее имя
(`CommunityCheckError`) обещало только проверку, а несли им два десятка
разных отказов. Наследниками разведены случаи, где от отказа зависит
поведение: `BotMessageGoneError` — сообщения, которое бот собрался
править, больше нет; `BotNotInCommunityError` (ADR-0035) — бота
в сообществе нет (не добавлен, выгнан, заблокирован; Bot API отвечает
403, распознаётся по классу исключения) — перепроверка по нему пишет
боту «не состоит», иначе выгнанный бот оставался бы в снимке
администратором навсегда. Дозор кнопок по нему снимает
обещание сразу, а не ходит за исчезнувшим постом сутки; правка кнопок
вышедшего поста переводит его в тот же `PublishedGoneError`, что
и правка текста, — на одну причину человек получает один совет.
Кода у этого отказа Bot API не даёт (400 и описание словами,
в отличие от типизованного `MESSAGE_ID_INVALID` у MTProto), поэтому
распознаётся он по описанию — список короткий и назван в коде.

Бот-путь (aiogram) переводит ошибки симметрично: флуд-лимит
(`RetryAfter`) — «Telegram просит подождать N с», превышение размера
файла — про лимит (а не ложное «нет связи»), серверные сбои (5xx) —
запасной веткой; текст поста при отправке ботом конвертируется
из разметки поля (`**жирный**`) в HTML — подписчики бот-канала видят
то же начертание, что и в userbot-канале (2026-08-15).
